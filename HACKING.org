* What this document is
:PROPERTIES:
:CUSTOM_ID: what-this-document-is
:END:

lambdock is a small program with a deliberately unusual shape: a C core that
draws, and an embedded Lisp that decides. This guide is the bridge between
reading the code and changing it safely.

** Who it is for
:PROPERTIES:
:CUSTOM_ID: who-it-is-for
:END:

- *You, if you are new to the tree.*  Read [[#introduction-and-mental-model][Introduction & mental model]],
  then [[#data-flow][Data flow]], then [[#pitfalls][Pitfalls]]. That is 80% of what you need.
- *You, if you know C and GTK but not Lisp.*  [[#the-scheme-side][Module reference (Scheme)]]

** The 60-second orientation
:PROPERTIES:
:CUSTOM_ID: the-60-second-orientation
:END:

If you read nothing else, read this.

1. *Two runtimes, one process.* C owns the window, the widgets, the Wayland
   protocols, the animations and all memory. GNU Guile owns the configuration and
   can drive C from the inside.
2. *Scheme decides /what/; C decides /how/ and /when/.* Intent and user
   configuration live in Lisp; rendering and resource ownership live in C.
3. *Everything UI is on the GTK main thread.* The REPL is a different thread and
   must never touch GTK directly; it goes through ~g_idle_add~.
4. *Configuration path:* =settings*.scm= → isolated Scheme evaluation → alist →
   ~<dock-config>~ record in ~*dock-configs*~ → C reads it through
   =guile_bridge.c= into ~LambdockState~.
5. *Items path:* Scheme ~<dock-item>~ records → ~populate_dock_items_for~ →
   GTK buttons/dynamic labels/separators appended to ~state->box~.
6. *Windows path:* the compositor's foreign-toplevel manager → =toplevel_tracker.c=
   → ~DockItem~ + ~AppWindow~ → running indicator and the window popover.
7. *Reload path:* =GFileMonitor= on =~/.config/lambdock= → 150 ms debounce →
   ~sync_docks_with_disk~ → create/reload/destroy dock instances.
8. *Ownership:* ~LambdockState~ owns its items, window trackers, monitor ref,
   size group and CSS providers. Free items through ~free_dock_item~ and docks
   through ~destroy_dock_instance~ -- never ~g_free~.
9. *Stored Scheme values must be protected* with ~scm_gc_protect_object~ (see
   ~DockItem::poll_fn~) and unprotected when freed.
10. *Test with ~maak test~* (rebuilds =build/= and runs the suite on a virtual
    display, so it also works over SSH), *and use an ASAN build for anything
    touching memory.* Run the uninstalled binary from the repository root (see
    the ~%load-path~ pitfall in [[#build-packaging-hazards][Build & packaging hazards]]).

** The four layers

| Layer                   | Lives in                                  | Answers                                                  |
|-------------------------+-------------------------------------------+----------------------------------------------------------|
| 1 · decisions           | =src/core/=                                | "given these values, what should happen?"                |
| 2 · process & platform  | =src/*.c=                                  | "who owns the docks, the proxies, the Scheme runtime?"   |
| 3 · one dock            | =dock_window.c=, =ui/dock_item.c=          | "how does one dock look, slide, and track windows?"      |
| 4 · panels & widgets    | =src/ui/*.c=                               | "how is one feature drawn and driven?"                   |

Layer 1 is the interesting one: it is where a change is cheap, because everything
there is a function of plain values. Layers 3 and 4 are where a change is
expensive, because the state they move is widgets.

** Dependency rules
:PROPERTIES:
:CUSTOM_ID: dependency-rules
:END:

- *=ui/= may include =core/=, never the reverse.* There is one known leak:
  =core/dock_dims.h= includes =ui/shelf.h= (for =LambdockShelfGeometry=), and
  =core/config_values.h= includes =lambdock.h= (for =LambdockShelfParams=).
  =core/dock_motion.c=, =core/item_text.c= and =core/tracker_rules.c= are
  genuinely GTK-free and their test binaries link nothing but GLib;
  =config_values= and =dock_dims= are pure in content but typed against the
  central header, so their tests link GTK. Moving the shelf/dock value structs
  into =core/= would close the loop.
- *Only three files touch Guile's C API:* =guile_bridge.c= (all config reads),
  =ui/dock_item.c= (calling a stored poll procedure) and =main.c= (starting the
  REPL). Anything else that needs Scheme asks the bridge.
- *Everything is on the GTK main thread, except the REPL*, which hops over with
  ~g_idle_add~. There are no locks anywhere and adding one is a sign the design
  went wrong.
- *Widgets are borrowed, state is owned.* A ~GtkWidget*~ field in ~LambdockState~
  or ~DockItem~ is a borrowed pointer that GTK destroys; lists of items, window
  trackers, CSS providers and strings are owned and freed by the module that
  created them. See [[#lifecycles][Lifecycles]].

** Inside a file, top to bottom
:PROPERTIES:
:CUSTOM_ID: inside-a-file
:END:

Files are ordered the same way, so a reader always knows where to look:

1. *types* — value structs that describe /what to do/, no widgets touched
2. *pure helpers* — decisions from values alone, no side effects
3. *side-effecting helpers* — one concern each (mutate one widget, one dock)
4. *callbacks* — thin adapters: read inputs, call the helpers above
5. *public API / ~main~*

=dock_window.c=, =toplevel_tracker.c=, =ui/launchpad.c= and =ui/preferences.c=
all follow it and say so in their header comment; when a file needs a sixth
section, it is usually two modules. Functions stay under ~40~ lines: the largest
one left (=lambdock_meter_snapshot= in =ui/meter.c=) is the next thing to split.

** The tables (one row or visitor per case)
:PROPERTIES:
:CUSTOM_ID: the-tables
:END:

Repeated cases are data, not switches. If you add a case, add a row:

| Table                                | File                | One row is...                            |
|--------------------------------------+---------------------+------------------------------------------|
| =ITEM_KIND_OPS=                      | =ui/dock_item.c=    | one kind of dock item (app, stack, …)     |
| =DOCK_ITEM_BUILDERS=                 | =guile_bridge.c=    | one Scheme item type                     |
| =STACK_VIEW_OPS=                     | =ui/stack.c=        | one stack view (grid / list)              |
| =k_*_switches=, =k_*_scales=, …      | =ui/preferences.c=  | one settings control                     |
| =k_*_actions=                        | =ui/preferences.c=  | one "do something" row (e.g. add a widget) |
| =DockVisitor= + ~dock_registry_foreach~ | =dock_registry.c= | one "do this to every dock" action        |

The last one is how a compositor event reaches every dock: the tracker defines one
visitor per event and hands it to ~dock_registry_foreach~, which walks a snapshot.
Never hand-roll the snapshot loop -- that is how five copies of it accumulated once
already.

* Introduction & mental model
:PROPERTIES:
:CUSTOM_ID: introduction-and-mental-model
:END:

lambdock is two runtimes living in one process:

- A *C core* built on [[https://gtk.org/][GTK4]] and
  [[https://github.com/wmww/gtk4-layer-shell][gtk4-layer-shell]]. It owns the
  window, the widgets, the CSS, the Wayland protocols, the animations, and all
  memory.
- An *embedded GNU Guile Scheme engine* that owns the /configuration/ and, at
  runtime, can drive the C core through exported primitives.

The division of responsibility is deliberate and is the single most important
thing to internalize:

| Concern                                    | Lives in        | Notes                                                |
|--------------------------------------------+-----------------+------------------------------------------------------|
| Screen surface, widgets, rendering         | C (GTK4)        | Must run on the GTK main thread                      |
| Wayland layer shell / foreign toplevel     | C (raw Wayland) | No Scheme in the event path                          |
| Memory ownership of state/items/windows    | C               | Scheme never allocates the structs it reads          |
| User configuration (per dock)              | Scheme          | Parsed by C callbacks, stored in a Scheme hash table |
| Item model (launchers, separators, widgets)| Scheme records  | Converted to GTK widgets by C                        |
| Live introspection / mutation              | Scheme          | REPL thread calls C primitives (marshalled)          |
| CSS theme resolution & scoping             | C               | Loaded from [[https://docs.gtk.org/gio/struct.Resource.html][GResource]], scoped per dock instance   |

A useful one-liner: *Scheme decides /what/ the dock contains; C decides /how/ it
is drawn and /when/ it is destroyed.* When in doubt about where a change belongs,
ask whether it is about /intent/ or /user configuration/ (Lisp/Scheme) or
/rendering and resources/ (C).

Because the two runtimes share a process, several hazards come from the seam
between them (threading, GC, allocators). See the section on
[[#pitfalls][Pitfalls & things to be careful about]].

The user-facing half of the documentation -- features, configuration options,
themes, the REPL and the item DSL -- lives in [[file:README.org][README.org]]; this file only covers
the parts a person changing the code needs.

** Tests
:PROPERTIES:
:CUSTOM_ID: tests
:END:

~meson test~ drives two kinds of suites: GLib/GTK C binaries (one per unit) and a
pure-Guile suite for the Scheme engine.

#+begin_src sh
meson test -C build                 # everything
meson test -C build --list          # list suite names
meson test -C build scheme_unit_tests
# or a single binary directly
./build/test_dock_item
# or the Scheme suite standalone
./tests/run_scheme_tests.sh
#+end_src

C unit binaries (in ~tests/~), each built from ~tests/test_<unit>.c~. The pure ones
link nothing but GLib (plus libm), which is the point: they prove a module needs no
display to be tested.

- *Pure, no GTK by design* -- =test_dock_click= (the click policy: launch,
  minimize, restore or list), =test_dock_motion= (easing/geometry),
  =test_item_text= (all wording and plurals), =test_tracker_rules= (window-tracking
  decisions), =test_dock_registry= (the dock list, snapshot and ~foreach~).
- *Pure logic, GTK-linked* -- =test_config_values= (clamps, name→enum rules),
  =test_dock_dims= (capsule/overlay/margin arithmetic); their headers pull in
  =lambdock.h= for the shelf structs, so the binaries link GTK.
- *One module, no dock* -- =test_icon_resolver=, =test_icon_zoom=,
  =test_theme_engine=, =test_shelf=, =test_meter=, =test_desktop_entry=,
  =test_app_actions=, =test_trash=, =test_accessibility=.
- *Full application context* -- =test_dock_item= (item lifecycle, window tracking,
  alignment, exec matching), =test_guile_bridge= (every C↔Scheme getter,
  exclusions, populate), =test_dock_window= (monitor validation, dimension maths,
  auto-hide, teardown), =test_popover_menu= (menu layouts per window count),
  =test_stack=, =test_launchpad=, =test_preferences=, =test_dock_dnd=,
  =test_config_startup=.
- =test_config_startup= is the one to know about: =test_guile_bridge= swaps in a
  *mock* ~(lambdock core)~, so nothing there proves that a real settings file plus
  the two override files in =$XDG_STATE_HOME= produce the values the dock reads.
  This binary loads the real Scheme modules through the real bridge, in a
  throwaway ~HOME~, and asserts the theme, a shelf number and the item order.

The Scheme suite (~tests/scheme/lambdock_tests.scm=, run by
[[file:tests/run_scheme_tests.sh][tests/run_scheme_tests.sh]]) loads the real
~scheme/lambdock~ modules under Guile and needs neither a display server nor the
C runtime. It is skipped (exit 77) when no Guile interpreter is available.

On a machine with no compositor -- a CI runner, a TTY, an SSH session -- run the
suite the way ~maak test~ does:

#+begin_src sh
maak test                      # whole suite, pinned Guix env, virtual display

# the same by hand, from a shell that has the packages of manifest.scm
GTK_A11Y=test GDK_BACKEND=x11 \
  xvfb-run -a -s "-screen 0 1024x768x24" meson test -C build --print-errorlogs
#+end_src

Four caveats, in the order they bit us:

- *The C tests need a display.* They call ~gtk_init_check()~
  ([[https://docs.gtk.org/gtk4/func.init_check.html][GTK docs]]) and return 77
  ("skipped") when it fails, but GTK emits its warnings -- no session bus, no
  icon theme -- *before* that check, and [[https://docs.gtk.org/glib/testing.html][g_test]]
  makes GLib warnings fatal. In a headless shell the C tests therefore abort with ~SIGTRAP~ instead of skipping. Hence ~xvfb-run~.
- *Accessibility needs a backend.* The accessible-name assertions read labels
  back through ~gtk_test_accessible_check_property()~, which aborts with
  ~gtk_at_context_get_accessible_property: assertion 'GTK_IS_AT_CONTEXT (self)'
  failed~ when GTK has no AT context. There is no a11y bus on a CI runner, so
  ~GTK_A11Y=test~ (GTK's own test backend) is exported by ~meson.build~, ~maak
  test~ and the Nix ~checkPhase~; the tests then check the real labels instead
  of skipping.
- *An icon theme is required.* =test_dock_item= and =test_guile_bridge= build
  items whose icon is ~utilities-terminal~, resolved through ~GtkIconTheme~, and
  they treat the "falling back to =application-x-executable=" warning as a
  failure. ~adwaita-icon-theme~ is in =manifest.scm= for that reason.
- A build directory is pinned to the Meson version that created it. Reading an
  old tree with a newer Meson fails with ~"Build data file ... references
  functions or classes that don't exist"~; use ~meson setup --reconfigure build~,
  a fresh directory, or ~maak test~, which discards =build/= first.
- ~detect_leaks=1~ exits non-zero on the third-party EGL/fontconfig/GLib leaks
  described under [[#sanitizers][Sanitizers]] below. To run the whole suite green use
  ~ASAN_OPTIONS=detect_leaks=0 meson test -C build-asan~ and check leak stacks
  separately for frames in ~src/~.

** Sanitizers
:PROPERTIES:

Because lambdock leaks and dangling pointers are easy to introduce, use
[[https://clang.llvm.org/docs/AddressSanitizer.html][AddressSanitizer]] /

** Verifying a change
:PROPERTIES:
:CUSTOM_ID: verifying-a-change

The short version, in the order that catches the most expensive mistakes first:

#+begin_src sh
# 1. Clean compile - the build treats warnings as errors

# 2. The whole suite, headless-safe: rebuilds build/ and runs it on Xvfb

- Compile is clean under ~-Werror~ (see [[#build-packaging-hazards][Build & packaging hazards]]).
- ~maak test~ passes: the C suite, the Scheme suite and the desktop/AppStream
  checks, with nothing skipped for lack of a display.
- New C behaviour has a case in the matching =tests/test_*.c=; new configuration
  or item behaviour has one in =tests/scheme/lambdock_tests.scm=.
- If you added a source, callback or provider, you added the matching teardown
  ([[#source-signal-lifecycle-rules][Source / signal lifecycle rules]]).
- New user-visible strings are wrapped in ~(G_ "...")~ and ~maak i18n-update~
  has been run.
- Documentation moved with the code: [[file:README.org][README.org]] for user-facing
  behaviour, this file for internals, [[file:NEWS.org][NEWS.org]] for what changed.
- If the change fixes one of the [[#pitfalls][Pitfalls]], move it out of the
  pitfall list in the same commit.

** The central struct
:PROPERTIES:
:CUSTOM_ID: the-central-struct
:END:

=lambdock.h= is the single source of truth for types. Read it before anything
else. ~LambdockState~ groups a dock instance's entire C-side world:

- Widgets: ~window~, ~overlay~, ~bg_capsule~, ~scrolled_window~, ~box~,
  ~popover~, ~size_group~.
- Config mirror (read from Scheme): ~auto_hide~, ~show_when_clear~,
  ~track_windows~, ~hover_animate~, ~icon_size~, ~theme~, ~config_path~, ~edge~,
  ~orientation~.
- Animation: ~tick_cb_id~, ~anim_start_time~, ~current_margin~, ~start_margin~,
  ~target_margin~, ~is_hidden~, ~hide_timer_id~.
- Ownership lists: ~dock_items~ (~GList~ of ~DockItem*~, see
  [[https://docs.gtk.org/glib/struct.List.html][GList]]) and ~window_trackers~
  (~GList~ of raw ~zwlr_foreign_toplevel_handle_v1*~).
- ~monitor~ (a /referenced/
  [[https://docs.gtk.org/gdk4/class.Monitor.html][GdkMonitor]] or NULL),

  providers.

=AppWindow= is the (window-handle, title) pair tracked per dock item. ~DockItem~
is described in [[#dock-item-lifecycle][Dock item lifecycle]].

One ~LambdockState~ == one GTK window == one ~settings*.scm~ (or the fallback).

* Data flow
:PROPERTIES:
:CUSTOM_ID: data-flow
:END:

This is the heart of the guide. Follow a change from a file on disk to pixels,
then back.

** 1. Configuration: file → Scheme table → C mirror
:PROPERTIES:
:CUSTOM_ID: data-flow-configuration
:END:

#+begin_src mermaid
flowchart LR
    F["~/.config/lambdock/settings*.scm"] --> L["(lambdock loader)\nresolve-dock-configuration\nisolated module eval"]
    L --> AL["association list\n((dock-position . bottom) ...)"]
    AL --> CORE["(lambdock core)\nload-dock-config! maps keys\n(both 'dock-x and 'x)"]
    CORE --> CONF["configure-dock!\n(lambdock state)"]
    CONF --> HT["*dock-configs* hash-table\nkeyed by config-path AND 'default"]
    BRIDGE["guile_bridge.c\nscm_c_public_ref + scm_call_*"] -->|reads| HT
    BRIDGE --> STATE["LambdockState fields"]
#+end_src

Details:

- =loader.scm:resolve-dock-configuration= evaluates the settings file inside a
  *fresh user module* (~make-fresh-user-module~), /shadowing/ ~define-module~ so
  the file cannot switch modules, and makes ~(lambdock core/items/presets)~
  visible. It then extracts every locally-bound variable into an alist. Any
  exception is caught and logged; a bad file yields ~'()~ rather than crashing.
- =core.scm:load-dock-config!= looks up each key, tolerating both namespaced
  (~dock-position~) and short (~position~) spellings, applying defaults, and
  calling ~configure-dock!~ with ~#:config-path file-path~.
- =state.scm= stores a ~<dock-config>~ record in the ~*dock-configs*~ hash table
  under the file path. If the path is ~'default~ /or/ ends in ~settings.scm~, it
  /also/ writes the record under the ~'default~ key. This aliasing is why "the
  primary settings file" can be reached without a path.
- C reads this table through =guile_bridge.c=, which resolves public procedures
  (~scm_c_public_ref~) and calls them with the dock's ~config_path~, converting
  Scheme values to C.

** The two override files (and when they are read)
:PROPERTIES:
:CUSTOM_ID: data-flow-overrides
:END:

The settings file is the source of truth, but two state files are layered on top
of it. Both are read *during* ~load-dock-config!~ -- i.e. at startup, on every
settings-file change, and on every reload -- so they need no "apply" action:

| File (under =$XDG_STATE_HOME/lambdock/=) | Written by        | Applied in                                  |
|-----------------------------------------+-------------------+---------------------------------------------|
| =preferences-<stem>.scm=                | Preferences window | ~load-dock-config!~: ~apply-dock-preferences~ prepends the pairs to the settings alist |
| =layout-<stem>.scm=                     | drag and drop     | ~state.scm:get-dock-items~: ~apply-dock-overrides~ rewrites the item list on every read |

Four things are worth knowing before debugging "my layout/preferences are not
applied":

- *The stem is the settings file's basename.* =settings.scm= → =layout-settings.scm=,
  so a second settings file (=settings-desktop.scm=) has its own pair.
- *Preferences are prepended, so they win.* ~assq~ finds them before the value
  the settings file defined; deleting the file restores the settings value.
- *=order= only reorders; it cannot resurrect an item.* Restoring an item needs
  its icon and command, and only the =added= section stores those (because only
  items dragged *in from outside* are recorded there). A key that is in =order=
  but in neither the settings file nor =added= is skipped -- loudly, since
  v0.15.0: ~N stored order key(s) are not in this dock any more~.
- *There is no in-process cache of either file.* They are re-read whenever they
  are needed, so a file written by another dock, by hand, or by a regenerated
  settings file is always current. (Layout mutations pass the layout they just
  built to the writer instead of reading it back, which is what makes a
  read-modify-write safe without a cache.)

Both loaders log what they did, which is the fastest way to answer "did it read
my file?": =Applied N GUI preference(s) for <path>: <keys>= and =Applied layout
for <path>: N ordered, N removed, N added=.

The bridge helpers are the pattern to copy:

#+begin_src c
static SCM call_core_proc_with_path(const char *func_name, const char *path);
static char *get_guile_string_for(const char *func, const char *module,
                                  const char *path, const char *default_val);
static gboolean get_guile_bool_for(const char *func, const char *path);
#+end_src

Then thin typed wrappers: ~get_autohide_config_for~, ~get_position_config_for~,
~get_theme_config_for~, ~get_monitor_config_for~, ~get_icon_size_config_for~,
~get_track_windows_config_for~, ~get_show_when_clear_config_for~,
~get_hover_animate_config_for~, ~get_repl_config_for~, and
~is_app_excluded(app_id, path)~.

The key names, their defaults and their meanings are tabulated for users in
[[file:README.org::#configuration-options][README: Configuration options reference]].

** 2. Items: Scheme records → GTK widgets
:PROPERTIES:
:CUSTOM_ID: data-flow-items
:END:

=populate_dock_items_for(state)= in ~guile_bridge.c~:

1. Calls ~get-dock-items~ for ~state->config_path~ (an SCM list).
2. For each element, reads ~dock-item-type~ and dispatches:
   - ~'app~ → ~create_dock_item(...)~ (favorite launcher).
   - ~'dynamic~ → reads ~dock-item-poll-fn~ and ~dock-item-poll-interval~, then
     ~create_dynamic_dock_item(...)~.
   - ~'separator~ → ~create_separator_dock_item(...)~.
   - ~'stack~ → ~create_stack_dock_item(...)~ (folder popover).
   - ~'launchpad~ → ~create_launchpad_dock_item(...)~.
   - ~'trash~ → ~create_trash_dock_item(...)~ (desktop trash, see
     =ui/trash.c=).
3. Each ~create_*~ builds the GTK button/popover, appends it to ~state->box~, and
   appends the ~DockItem*~ to ~state->dock_items~.

The record and constructors live in =items.scm=; the dispatch reads the
*public* accessors (~dock-item-name~ etc.), so the internal ~%dock-item-*~
accessors can change freely as long as the public wrappers stay stable.

The item DSL as users see it (including the presets and dynamic widgets) is
documented in [[file:README.org::#the-dock-dsl][README: The dock DSL: items and presets]].

** What a click does (minimize to dock)
:PROPERTIES:
:CUSTOM_ID: data-flow-click
:END:

A left click on an application item is one function:
=core/dock_click.c:lambdock_click_action_for(window_count, window_minimized,
window_active, launcher_command)= returns one of

| Action                     | When                                                | Applied by                                              |
|----------------------------+-----------------------------------------------------+---------------------------------------------------------|
| =LAMBDOCK_CLICK_LAUNCH=    | no window, and a launcher command exists            | ~g_spawn_command_line_async~                            |
| =LAMBDOCK_CLICK_MINIMIZE=  | one window, focused and not minimized               | ~minimize_toplevel_window~ (set_minimized)              |
| =LAMBDOCK_CLICK_ACTIVATE=  | one window, minimized or in the background          | ~activate_toplevel_window~ (unset_minimized + activate)  |
| =LAMBDOCK_CLICK_MENU=      | two or more windows                                 | the window popover                                      |
| =LAMBDOCK_CLICK_NOTHING=   | no window and no launcher command                   | nothing                                                 |

The two flags come from the compositor: =toplevel_tracker.c= parses the ~state~
event's array into ~MasterToplevel.minimized~/~.activated~ and mirrors them onto
every dock's ~AppWindow~ (the records ~DockItem.windows~ points at). That is why
the rule is testable without a compositor -- =tests/test_dock_click.c= passes
counts and booleans in.

Two consequences worth knowing:

- *Minimize is a request, not a command.* ~set_minimized~ is advisory, and a
  compositor with no minimize concept (scrollable tiling ones, niri included)
  ignores it: the click becomes a no-op instead of doing something wrong.
- *Multi-window items do not minimize.* With several windows the click still
  opens the popover, because "which window did you mean" has no good answer; the
  popover's per-window rows are the place for per-window actions.

** 3. Window tracking: compositor → items → popover
:PROPERTIES:
:CUSTOM_ID: data-flow-windows
:END:

#+begin_src mermaid
flowchart TD
    REG["wl_display_get_registry\nregistry_handle_global"] -->|binds| MGR["zwlr_foreign_toplevel_manager_v1"]
    MGR -->|toplevel| NEW["manager_handle_toplevel\nMasterToplevel + listener"]
    NEW --> APPID["toplevel_handle_app_id"]
    NEW --> TITLE["toplevel_handle_title"]
    NEW --> CLOSED["toplevel_handle_closed"]
    APPID -->|for each active dock| FIND["find_dock_item_by_app_id\nor create dynamic item"]
    FIND --> ADDW["dock_item_add_window(item, handle)"]
    APPID --> WT["state->window_trackers append handle"]
    CLOSED --> REMW["dock_item_remove_window + free empty dynamic item"]
    CLOSED --> WTR["window_trackers remove handle; reveal if clear"]
    ADDW --> UPD["update_dock_item_status -> 'running-app',\n'window-focused', 'window-minimized' classes"]

- ~init_toplevel_tracker()~ binds the manager exactly once (guarded by
  ~tracker_initialized~), even though it is called per dock instance.
- Incoming events are broadcast to /every/ active dock; each dock filters via
  ~is_app_excluded()~ and matches/creates an item.
- ~sync_window_trackers(state)~ replays all known toplevels into a dock's items;
  it is called when a dock is created and after every reload.
- Popovers (=popover_menu.c=) render the per-item window list, with "focus",
  "close", "new instance", and "close all". Every row carries a symbolic icon,
  the window holding the focus is marked and minimized windows are dimmed, and
  =lambdock_popover_menu_keys()= gives the menu Up/Down/Home/End while the same
  controller stays inert on a stack panel (it checks for the =popover-menu=

[[https://wayland.app/protocols/wlr-foreign-toplevel-management-unstable-v1][zwlr_foreign_toplevel_management_unstable_v1]]

** 4. Hot reload & reconciliation
:PROPERTIES:
:CUSTOM_ID: data-flow-reload
:END:

#+begin_src mermaid
flowchart TD
    FM["GFileMonitor 'changed' on ~/.config/lambdock"] --> CB["on_file_changed_cb"]
    CB -->|restart| T["g_timeout_add(150ms)\ng_reload_timer_id"]
    T --> SYNC["sync_docks_with_disk(app)"]
    SYNC --> SCAN["scan_settings_files()\nsettings.scm or settings-*.scm"]
    SCAN --> KILLFALLBACK["destroy fallback docks if files exist"]
    SCAN --> KILLGONE["destroy docks whose file disappeared"]
    SCAN --> PERFILE["per file: load_dock_config_scm, start-repl!,\nreconcile monitors"]
    PERFILE --> NEWDOCK["create_dock_instance() or reload_dock_instance()"]
#+end_src

~sync_docks_with_disk~ is the single reconciliation entry point, also used by the
monitor-hotplug listener and at startup. It:

- Destroys file-less fallback docks when any settings file exists.
- Destroys docks whose config file was deleted.
- For each file, (re)loads its Scheme config, (re)starts its REPL if enabled, and
  reconciles monitor binding:
  - ~dock-monitor = 'all~ → one dock per connected monitor.
  - A connector name such as ~"DP-1"~ → resolved through
    ~find_monitor_by_connector()~; if no output matches, it logs a warning and
    falls back to the default monitor assignment.
  - Anything else (~'default~, empty) → one dock with ~monitor = NULL~, left to
    the compositor's default assignment.
- If /no/ settings files exist, spawns a single fallback dock
  (~config_path == NULL~).

The watcher is the =GFileMonitor= of [[https://docs.gtk.org/gio/class.FileMonitor.html][GIO]], debounced with
~g_timeout_add~ so that a burst of saves (editors writing several files, or a
~git checkout~) results in one reconciliation.

** 5. REPL / live mutation flow
:PROPERTIES:
:CUSTOM_ID: data-flow-repl
:END:

#+begin_src mermaid
flowchart LR
    SOCK["Unix socket thread\n(call-with-new-thread)"] -->|"(set-dock-theme! 'nature)"| SET["(lambdock state) setters"]
    SET --> TRIG["trigger-ui-reload! -> (reload-dock!)"]
    TRIG -->|C subr| IDLE["g_idle_add(on_manual_reload_idle)"]
    IDLE --> REDRAW["redraw_active_docks()\nreload_dock_instance() per dock"]
#+end_src

The crucial rule: the REPL runs on *another thread*. It must never touch GTK
directly. ~reload-dock!~ therefore schedules work onto the main loop with
~g_idle_add~ ([[https://docs.gtk.org/glib/func.idle_add.html][GLib docs]]).
Getters (~get-dock-*~), and the setters in =state.scm=, are safe to call from the
REPL because they only touch the Scheme hash table -- the setters end by calling
~trigger-ui-reload!~, which is where the hop back to the main thread happens.

The same hop is what the *launchpad* primitives use, so a dock is scriptable
beyond its configuration:

| Primitive                        | Does                                    |
|----------------------------------+-----------------------------------------|
| ~(show-launchpad!)~              | opens the launchpad of the first dock   |
| ~(launchpad-search! "calc")~     | types into its search field             |
| ~(hide-launchpad!)~              | closes it                               |

They are what =tools/record-demo/= drives to film the launchpad without a
virtual keyboard, and they are useful from a settings file or a REPL session:

#+begin_src scheme
(begin (show-launchpad!) (launchpad-search! "term"))
#+end_src

** The one thing that is *not* safe from two threads: Guile itself
:PROPERTIES:
:CUSTOM_ID: repl-guile-thread-hazard
:END:

Marshalling widgets to the main loop is enough for GTK, but the main thread also
*calls into* Scheme (every ~get-dock-*~ getter, every item accessor). If the REPL
thread is evaluating at the same moment, the two evaluators share module state.
A Scheme error raised from the main thread has no handler there, so Guile aborts
the process -- that is how "In thread: Wrong type to apply: #f" became a crash
while a REPL-driven reload was rebuilding the dock with reflections on.

Two defences are in place, and both are worth keeping:

- =guile_bridge.c:resolve_item_accessors()= validates *every* accessor it will
  later call, not a sample. A module that failed to export one of them degrades
  to "no items" instead of applying ~#f~.
- =ui/dock_item.c:refresh_dynamic_item()= returns early when the item has no
  poll procedure, so nothing can apply ~#f~ from a poll path.

The remaining hazard is inherent to embedding a REPL in the same process: do not
assume a REPL-driven reload and a REPL expression are isolated from each other.
Serialise them (wait for the reload to settle) when a script depends on the
result, which is what the recorder's storyboard does.

The GTK *Preferences* window (=src/ui/preferences.c=) is the other caller of the
same setters. It runs on the main thread, so it can call them directly; each edit
goes through the ~set-dock-preference!~ dispatch in =scheme/lambdock/prefs.scm=,
which applies the ordinary setter and then records the value in a GUI override
file under ~$XDG_STATE_HOME/lambdock~. ~load-dock-config!~ layers that file over
the settings file, so a generated settings file can be regenerated without losing
the choices made in the window. The debounced apply in =preferences.c= exists
because a slider emits ~value-changed~ on every pixel and each edit rebuilds the
dock.

* Lifecycles
:PROPERTIES:
:CUSTOM_ID: lifecycles
:END:

** Dock instance lifecycle
:PROPERTIES:
:CUSTOM_ID: dock-instance-lifecycle
:END:

*Create* -- ~create_dock_instance(app, monitor, config_path)~ (in ~main.c~):

1. Allocate ~LambdockState~, ~g_object_ref~ the monitor, connect its
   ~invalidate~ signal to immediately unbind layer-shell.
2. Read position/orientation, create the window, load theme CSS, read the rest of
   the config into fields.
3. Build the widget tree: overlay → background capsule + scrolled viewport → box;
   attach the scroll controller; ~update_dock_dimensions~; size group.
4. Rebuild items (~populate_dock_items_for~).
5. Build the app context popover (About/Quit) and the right-click gesture.
6. ~setup_layer_shell_window~ + ~setup_dock_motion_controller~.
7. Append to ~g_active_states~ and connect ~window "destroy" →
   destroy_dock_instance~.
8. ~gtk_window_present~, ~init_toplevel_tracker~, ~sync_window_trackers~.
9. Apply initial auto-hide behavior.

*Reload* -- ~reload_dock_instance(state)~ (in ~dock_item.c~): re-read theme and
CSS, cancel the hide timer, hot-swap edge/orientation (un-anchor old edge,
re-anchor new), re-read booleans/icon size, ~clear_favorite_dock_items~ +
~populate_dock_items_for~, ~sync_window_trackers~, re-align all items,
~update_dock_dimensions~, and re-apply auto-hide/exclusive-zone policy.

*Destroy* -- ~destroy_dock_instance(state)~ (in ~dock_window.c~). The order
matters and is the canonical teardown sequence:

1. Set ~is_destroying = TRUE~ (re-entrancy guard; the ~"destroy"~ signal will
   re-enter this function).
2. Remove CSS providers from the display; free ~active_theme_class~.
3. ~unregister_dock_state(state)~ (removes it from ~g_active_states~).
4. Remove the hide timer and the tick callback.
5. ~g_signal_handlers_disconnect_by_data(window, state)~.
6. Unparent the popover.
7. Free all dock items (list is detached first so nothing can walk it during
   free), then free the window-tracker list.
8. Null out ~window~ / refs, ~gtk_window_destroy~, unref ~size_group~, unref
   ~monitor~, free ~config_path~, ~theme~, and finally the ~state~.

*Never* free a ~LambdockState~ by hand; always go through
~destroy_dock_instance~ so timers/handlers/providers are cleaned up.

** Dock item lifecycle
:PROPERTIES:
:CUSTOM_ID: dock-item-lifecycle
:END:

=ui/dock_item.c= owns ~DockItem~:

- ~create_dock_item~: favorite app launcher (button + image + popover + right
  click gesture). ~is_favorite = TRUE~.
- ~create_dynamic_dock_item~: label widget + poll timer + protected Scheme thunk.
  ~is_favorite = TRUE~ (so it is recreated on reload from config).
- ~create_separator_dock_item~: a ~GtkSeparator~
  ([[https://docs.gtk.org/gtk4/class.Separator.html][GTK docs]]) (note: not a
  [[https://docs.gtk.org/gtk4/class.Button.html][button]] -- helpers must
  null-check with ~GTK_IS_BUTTON~). ~is_favorite = TRUE~.
- ~create_trash_dock_item~: an icon item whose artwork follows the trash, plus a
  refresh timer (~trash_timer_id~) that re-counts it. The counting and emptying
  live in =ui/trash.c=, against the freedesktop.org trash layout; nothing about
  it is desktop-specific.  =ui/dock_dnd.c= gives the item a drop target for
  file lists, which hands each dropped file to ~lambdock_trash_file()~ (GIO's
  ~g_file_trash()~) on a worker thread.
- Tracked (running-window) items created by the tracker use
  ~create_dock_item(..., is_favorite = FALSE, ...)~ and are removed automatically
  when their last window closes.
- ~free_dock_item~: cancels the poll timer, unprotects and clears the Scheme
  thunk, disconnects popover/button handlers, unparents/unparents-and-removes
  widgets, frees every ~AppWindow~, then the strings and the struct.
- ~clear_favorite_dock_items~: walks ~state->dock_items~ and frees only
  ~is_favorite~ items, leaving tracked (non-favorite) items in place. Used by
  reload before repopulating.

The reason the two kinds are separated is reload: after a config edit the pinned
launchers are rebuilt from Scheme, while items that exist only because a window is
open must survive that rebuild untouched.

** Source / signal lifecycle rules
:PROPERTIES:
:CUSTOM_ID: source-signal-lifecycle-rules
:END:

Every GLib/GTK source that stores a raw pointer must be cancelled before that
pointer dies:

- Timers: ~hide_timer_id~, ~poll_timer_id~, ~trash_timer_id~ → ~g_source_remove~
  ([[https://docs.gtk.org/glib/struct.Source.html][GSource]]).
- Tick callbacks: ~tick_cb_id~ → ~gtk_widget_remove_tick_callback~
  ([[https://docs.gtk.org/gtk4/method.Widget.add_tick_callback.html][add_tick_callback]]).
- Signals: ~g_signal_handlers_disconnect_by_data~ (the data pointer is the key).
- Idle callbacks (~g_idle_add~) currently pass ~NULL~ data, so they cannot
  dangle.

* Code conventions: values in, values out
:PROPERTIES:
:CUSTOM_ID: code-conventions
:END:

The C side is deliberately boring about state.  A handful of rules cover most of
it, and the places that already follow them are where a new feature should land.

** Pure logic goes in =src/core/=
If a decision can be made from numbers and strings alone -- how thick the capsule
is, what a NaN shelf parameter should become, whether =taskbar= means taskbar --
it belongs in =src/core/=, takes values and returns values, and is unit tested
without a display or an interpreter (=tests/test_config_values.c=,
=tests/test_dock_dims.c=).  =update_dock_dimensions()= is then only appliers: read
a monitor, ask =lambdock_dock_dims_compute()= once, push the finished struct into
widgets.

** One owner per piece of mutable state
- The set of docks lives in =dock_registry.c=; nothing else keeps that list, and
  callers either iterate a snapshot or, preferably, hand a =DockVisitor= to
  ~dock_registry_foreach()~ -- destroying a dock inside the loop cannot corrupt
  the iteration either way.
- The foreign-toplevel tracker owns every Wayland proxy in one
  =ToplevelTracker= (=g_tracker= in =toplevel_tracker.c=). Docks hold *borrowed*
  handles in =state->window_trackers=, which is why ~free_window_tracker()~ is a
  documented no-op: the tracker frees the proxy when the window closes or the
  manager goes away.
- The launchpad is one model value (=LambdockLaunchpad= in =ui/launchpad.c=)
  rather than ten file statics, and the functions that act on it take it as a
  parameter; only its public entry points reach for the instance.
- ~AppWindow~ lists are freed through =app_window.c=, which is NULL-safe.
- Timer ids are cleared with ~g_clear_handle_id()~, or reset by the callback that
  consumed them, so teardown never removes a dead (possibly recycled) source.

** Decisions are extracted even when the caller is a protocol listener
The tracker's listeners are three lines each: cast the event data, call the pure
rule in =core/tracker_rules.c= (=lambdock_tracker_should_hide()=,
~..._item_should_be_dropped()~, ~..._ignores_app_id()~), then call one helper or
one visitor. "Should this dock hide?" is a function of three booleans, so it is
tested by =tests/test_tracker_rules.c= without a compositor. When a condition in a
callback needs more than one clause, it belongs in =core/= with a name.

** A kind is a table row, not a switch
- A dock item kind is one row of =ITEM_KIND_OPS= in =ui/dock_item.c=: key name,
  CSS class, click behaviour, accessibility text.  Adding a kind means adding a
  row and, if it needs one, a small builder.
- A Scheme item type is one row of =DOCK_ITEM_BUILDERS= in =guile_bridge.c=.
- The stack panel walks folders with three pure helpers -- =lambdock_stack_child_path=,
  =lambdock_stack_parent_path= and =lambdock_stack_breadcrumb= -- so the browsing
  rules are unit tested without a display; =lambdock_stack_panel_new()= builds
  the panel for any folder, and the popover only remembers *where* it is.
- A stack view is one row of =STACK_VIEW_OPS= in =ui/stack.c= (settings symbol +
  builder), which is also where the symbol mapping lives.

** Strings that leave the bridge are GLib strings
=guile_bridge.c= converts ~SCM~ values with ~scm_to_utf8_string()~ and copies them
with ~g_strdup()~; every caller frees with ~g_free()~.  Guile's ~malloc~'d strings
never escape the bridge, so every free site can be checked by grep.

** Small functions, lists of steps
Public entry points read as a short list of named steps: =create_dock_instance()=
is /read the settings → build the widgets → populate the items → build the menu →
install the input → present/, and each of those is a function.
=sync_docks_with_disk()= is /select the docks → destroy them → reconcile each
settings file/.

** The DSL
:PROPERTIES:
:CUSTOM_ID: the-dsl
:END:

Settings files are ordinary Guile programs. They define variables that the loader
extracts -- the conventional names are:

#+begin_src scheme
(define dock-auto-hide? #t)
(define dock-show-when-clear? #t)
(define dock-position 'bottom)      ;; 'bottom | 'top | 'left | 'right
(define dock-icon-size 48)
(define dock-theme 'vanilla)        ;; 'vanilla | 'vanilla-light | 'snow-leopard
                                    ;; | 'snow-leopard-dark | 'solarized-light
                                    ;; | 'nature | 'unity | 'macos-tiger
                                    ;; | 'macos-big-sur | 'macos-ventura
                                    ;; | 'macos-tahoe | 'macos-tahoe-dark
                                    ;; | 'macos-mavericks | 'macos-mavericks-dark
                                    ;; | 'windows-xp | 'windows-vista
                                    ;; | 'windows-7 | 'windows-10
                                    ;; | 'windows-11 | 'none
;; Or a whole dock in one line: theme + sizes + spacing + mode + shelf geometry
;; (recipes live in scheme/lambdock/looks.scm, see README: Looks).
;; (define dock-look 'osx-mavericks)
(define dock-monitor 'all)          ;; 'all | 'default | "DP-1"
(define dock-mode 'dock)            ;; 'dock | 'taskbar
(define dock-launchpad-close-side 'left) ;; 'left | 'right
(define dock-show-window-titles? #f)
(define dock-exclude-apps '())
(define dock-enable-repl? #f)
(define dock-repl-socket-path "/tmp/lambdock-repl.sock")
(define dock-hover-animate? #t)
(define dock-track-windows? #t)
(define dock-items
  (list (preset-launcher 'alacritty)
        (app-item #:name "Files" #:exec "nautilus" #:icon "system-file-manager")
        (separator-item)
        (ram-item) (clock-item)))
#+end_src

Item constructors: ~app-item~ (~#:name #:icon #:exec #:hover-animate?~),
~dynamic-item~ (~#:name #:icon #:exec #:poll-fn #:poll-interval
#:hover-animate?~), ~separator-item~. Presets: ~preset-icon~, ~preset-launcher~,
~preset-launchers-for~. Dynamic presets: ~ram-item~, ~clock-item~, ~cpu-item~,
~battery-item~, ~cpu-temp-item~.

Looks (whole-dock recipes) are a separate module, ~(lambdock looks)~, re-exported
by ~(lambdock presets)~ and ~(lambdock core)~ so a settings file sees them without
importing anything: ~dock-looks~, ~look-aliases~, ~look-settings~,
~look-setting~, ~look-name~, ~look?~, plus ~apply-look!~ for the REPL. The loader
resolves ~dock-look~ into that alist and reads it as a *fallback* beneath the
file's own definitions. Nothing in the C side knows about looks: they are just
the existing settings.

Defaults, accepted values and the full preset list are in
[[file:README.org::#configuration-options][README: Configuration options reference]]
and [[file:README.org::#the-preset-zoo][README: The preset zoo]].

** CSS & themes
:PROPERTIES:
:CUSTOM_ID: css-and-themes
:END:

Themes are GResource files at ~/org/jointhefreeworld/lambdock/css/<theme>.css~.
~load_custom_css~ is two halves: ~lambdock_theme_request~ (a pure function in the
same file) turns the dock's settings into a ~LambdockThemeRequest~ -- normalised
theme name, ~theme-<name>~ class, and which modifiers apply -- and the appliers
act on that value:

1. Swaps the per-instance scope class ~theme-<name>~ on the window.
2. Detaches the four providers the previous load installed (base theme, taskbar,
   shelf, user CSS) in one pass, so a reload swaps rather than stacks.
3. Loads the modifiers (~taskbar.css~ when taskbar mode or window titles are on,
   ~shelf.css~ when the glass geometry is), then the built-in theme, rewriting
   every selector through ~scope_css_selectors~ so rules only affect this dock
   and cannot leak between instances.
4. Layers user overrides from =~/.config/lambdock/styles.css= on top at
   ~GTK_STYLE_PROVIDER_PRIORITY_USER~.

Theme `none` is the request's ~disabled~ flag: the class and providers are still
swapped, but nothing is loaded.

Scoping rules: ~.foo~ becomes ~.theme-<name> .foo~; a selector starting with
~window~ becomes ~window.theme-<name>...~; ~@~-rules/comments pass through. This
is why a user override still needs to target the dock's own classes.

** State classes a theme can style
:PROPERTIES:
:CUSTOM_ID: css-state-classes
:END:

An item button carries ~dock-item~ and ~flat~ always, plus these as the running
state changes (all applied by =dock_item.c:apply_running_state()=):

| Class                | Means                                       | Typical use                                        |
|----------------------+---------------------------------------------+----------------------------------------------------|
| ~running-app~        | the application has at least one window     | indicator dot/pill, or a raised "task button"       |
| ~window-focused~     | one of its windows holds the keyboard focus | the lit/long indicator, or the Aero-lit tile        |
| ~window-minimized~   | all of its windows are minimized            | dim the icon (overlays.css does)                    |
| ~window-title-label~ | the label on the ~.window-title-label~ widget | the running window's title next to the icon      |

~window-focused~ and ~window-minimized~ are mirrored from the compositor's
~state~ event, so they flip within a frame of the user switching windows. Which
of the two a theme uses is a matter of fidelity to the desktop it imitates:

- the *Windows* themes use all three. XP raises a running button and depresses
  the focused one; Vista and 7 keep a quiet glass tile for running and light the
  focused one (Aero brightens instead of pressing); 10 and 11 draw a short
  underline/pill for running and the long one for the focused window.
- the *macOS* themes draw a dot for running apps and ignore ~window-focused~,
  because OS X does not distinguish. The dot is dark on the light slabs (Tiger,
  Snow Leopard, Mavericks) and white on the dark ones -- the same rule the C-side
  shelf dot follows: it paints a soft shadow under its white glow so the dot
  survives on the platinum and Aqua shelves.
- lambdock's own stock themes (vanilla, vanilla-light, solarized-light, nature,
  unity) draw a glow pill for running and widen/brighten it while focused.

Only [[https://docs.gtk.org/gtk4/css-overview.html][GTK CSS]] applies here, not
browser CSS; the properties are listed in
[[https://docs.gtk.org/gtk4/css-properties.html][the GTK CSS property reference]].
User-facing theming -- the nineteen built-in themes, the look recipes and how to
override them -- is in
[[file:README.org::#styling-and-theming][README: Styling & theming]].

*** Modifiers vs. themes
Modifier stylesheets are loaded *before* the base theme at the same provider
priority and scoped under the same ~theme-<name>~ class, so they add a behavior
(the taskbar layout, the glass shelf) to *any* theme while equal-specificity
theme rules keep winning:

| Modifier          | Loaded when                                       |
|-------------------+---------------------------------------------------|
| =css/taskbar.css= | ~dock-mode~ is ~'taskbar~ or window titles are on |
| =css/shelf.css=   | ~lambdock_shelf_active()~ (see below)             |

*** The glass shelf (one implementation, no modes)
There is no "second dock" and no preset layer. ~LambdockShelfParams~
(=src/lambdock.h=) describes the shape and the dock always runs the same widgets:

- ~tilt_deg~ / ~perspective~: how the capsule is projected away from the viewer.
- ~margin_px~ / ~front_px~: glass on the inner / outer side of the icons
  (a negative margin makes the icons overhang the shelf).
- ~reflection_ratio~ / ~reflection_intensity~ / ~reflection_blur_ratio~: the
  mirrored icon reflections.

Geometry is derived in ~lambdock_shelf_geometry_for()~ (=ui/shelf.c=):

#+begin_src c
band    = round(icon * reflection_ratio);
outer   = MAX(front_px, band);
capsule = icon + margin_px + outer;          /* dock_capsule_cross_dim() */
overlay = icon * CROSS_DIM_SCALE_FACTOR + CROSS_DIM_PADDING_PX
          + outer + MAX(0, -margin_px);      /* dock_cross_axis_dim() */
#+end_src

With the defaults (margin = 24, front 0, reflection 0) that is exactly the
classic ~icon + 24~ capsule, so the flat dock is untouched.

- ~lambdock_shelf_params_default()~ returns the flat defaults and
  ~lambdock_shelf_params_effective()~ also covers NULL/zero-initialised states.
- ~lambdock_shelf_active()~ is the single switch used by the CSS classes
  (~shelf-mode~, ~shelf-mirror~, ~shelf-<edge>~), the modifier stylesheet and
  the reflection widgets: TRUE when any geometric parameter deviates.
- ~LambdockShelfFrame~ (=ui/shelf.c=) wraps the themed capsule and re-renders it
  through a projective =GskTransform= (~gsk_transform_rotate_3d~ +
  ~gsk_transform_perspective~). GTK CSS transforms are affine only, which is why
  the tilt cannot live in the stylesheet; with ~tilt == 0~ the frame is a plain
  pass-through.
- ~LambdockReflection~ (=ui/shelf.c=) paints, per item: the contact shadow under
  the icon, the mirrored/blurred/faded copy, and the running-app glow dot near
  the outer edge. The fade uses a number of bands proportional to the band
  height (sub-pixel bands would be quantised away and leave gaps).
- ~apply_shelf_layout()~ shows/hides and sizes those widgets from the parameters
  and the fisheye state; ~update_dock_item_status()~ feeds the running dot.
- Scheme side: every parameter is a ~dock-*~ option plus a getter/setter, and
  ~core.scm~ reads each one independently (no presets, no modes).

Real backdrop blur needs the compositor (a layer-shell surface cannot sample what
is behind it); the frosted glass is drawn with gradients instead.

* Performance notes
:PROPERTIES:
:CUSTOM_ID: performance
:END:

The dock animates whenever the pointer moves, so these rules exist to keep
per-frame work proportional to *visible* items and nothing else.

** Measure it: /perf/ tests and the render counters
="src/core/render_stats.c"= keeps a handful of integer counters (hover frames,
frames dropped before touching a widget, item layout steps, geometry-cache
rebuilds, icon/reflection paints, surface resizes). They cost an increment and
they turn the interesting questions into numbers: "did hovering relayout the row?"
is answered by =layout_steps=, "did the surface keep its size?" by
=surface_resizes=.

=tests/test_render_budget.c= drives the real hover path against a hand-allocated
row (no window, so no compositor is involved) and asserts the budget. Current
numbers on a row of eight items, 40 frames sweeping the pointer across it:

| Counter                | Measured | Why it is the budget                                  |
|------------------------+----------+-------------------------------------------------------|
| =hover_frames=          |       40 | every frame ran                                       |
| =layout_steps=          |       91 | of 320 possible (frames × items): the 2 px stepper    |
| =geometry_refreshes=    |       31 | fewer than frames: the cache survives between steps   |
| =surface_resizes=       |        0 | a resize is a buffer re-allocation + recompositing    |

and 20 sub-pixel jitter frames (a trackpad) cost =0= layout steps and =0=
geometry rebuilds: =FISHEYE_POINTER_STEP_PX= drops them before they touch a
widget. A reflection repaint costs one clipped draw per fade band, and
=lambdock_reflection_band_count()= is pure and tested: 14 draws at the 14 px band
the macOS Mavericks shelf uses, 16 in the worst case.

** Where the time actually goes, and where it does not
The counters say *what* happens per frame; the interesting question after that is
how much of a frame is ours at all. =hover_us= accumulates the microseconds spent
inside =dock_apply_hover_at()= -- the cached geometry lookup, the bell curve per
item, the size requests -- and the budget test prints it as a per-frame figure
and asserts it stays a rounding error:

| Measurement (row of 8 items, 40-frame sweep)      | Value                |
|---------------------------------------------------+----------------------|
| the dock's own work per hover frame                | ~30 us (0.2 % of 16.7 ms) |
| whole-process CPU while idle, dock visible         | 0 jiffies in 10 s    |
| whole-process CPU while hidden                     | 0 jiffies in 6 s     |
| whole-process CPU during a 4 s hover over 27 items | ~7 % of one core     |

So the magnification's arithmetic is not what costs anything: the remaining 7 %
is GTK measuring, allocating and painting the row, which is what magnifying a row
of icons *is*. Adopting a coarser =FISHEYE_LAYOUT_STEP_PX= would trade that for
visible pops in the mirrors, and it is the one lever left -- so it has not been
pulled. What matters for a dock on a battery is the first two rows, and both are
zero because every tick callback is one-shot and every poll timer stops while the
dock is off screen.

Two more things the audit measured on a running session (niri, 1880x1253 at 1.2x,
27 items), because they are invisible until they are wrong:

- *Nothing is clipped at the ends of the row.* Sweeping the pointer onto the
  first and last item keeps the applied input region at least 25 px inside the
  surface on both sides (=rect 29,73 1640x76= in a 1698 px surface), and the row's
  neighbours keep their bottom edge (=y 146=) while the item under the pointer
  grows: the row does not jump vertically, it only widens.
- *The edge does not bounce.* Twelve crossings in and out of the dock in two
  seconds produce twelve leave/enter pairs, twelve hidden timers and zero hides --
  a real leave afterwards still hides it exactly once -- and twelve jitters along
  the trigger strip produce exactly one reveal. That is the settle window doing
  its job, measured rather than hoped for.

** The widget tree, and why it is shaped like this
#+begin_example
window (layer surface: anchored to the dock's edge, sized by the overlay)
└── overlay              cross-size request = magnification headroom
    ├── shelf frame      the theme's capsule, projected (tilt/flare) if asked
    │   └── capsule      CSS background; size-grouped with the row's width
    └── scroller         the row's viewport (only scrolls along the dock axis)
        └── row box      one container per item, spacing between them
            └── item container: [button → cell → icon/label] + [reflection]
#+end_example

Two decisions follow from the metrics:

- The *cell* inside each item's button is what carries the icon-sized size
  request, not the button: the theme's padding then sits outside the sum, so an
  icon, a label and a gauge are exactly as tall as each other.
- Every item owns a *reflection slot* even when it has nothing to mirror. The
  band the slot reserves is part of the cell's height; dropping it leaves gauges
  and separators a band lower than the icons on a shelf theme.

** Lifecycle: three clocks, and they never overlap
1. *Layout* changes only when something real changes -- icon size, spacing,
   padding, the item list, the mode, the shelf. =update_dock_dimensions()= is the
   single place that re-requests geometry, and it is called from a reload, not
   from a frame. It also invalidates the hover geometry cache
   (=state->centres_dirty=) and queues one input-region update.
2. *Animation* (the fish-eye) runs on one-shot frame ticks: a motion event
   records the pointer and arms one tick, the tick applies the newest position
   once, and nothing is left running. Its layout part is stepped to 2 px; its
   paint part is a transform, so magnification is continuous.
3. *Data* (clocks, gauges, trash counts) runs on per-item timeouts that skip
   their work while the dock is off screen, and are caught up in one pass when it
   reappears.

** One layout pass per frame, not per event
Motion events only record a position and arm one one-shot frame-clock tick
(=on_motion_notify= → =gtk_widget_add_tick_callback=, =dock_window.c=). The row is
scaled once per frame in =update_dock_items_fisheye()=, and skipped entirely when
the dock is hidden, sliding, or motion is reduced.

** Paint continuously, lay out coarsely
The fisheye magnifies by painting a transform (=ui/icon_zoom.c=), so the icon
follows the pointer exactly; only the *size request* steps. =lambdock_size_step()=
rounds magnified sizes to =FISHEYE_LAYOUT_STEP_PX= (2 px), which halves the row's
re-measures during a hover sweep -- =test_dock_motion.c= measures it: 23 distinct
sizes without quantising, 12 with, while the painted scale still changes at every
sampled position. The resting size is never rounded.

** The surface keeps its size while hovering
Growing the icons grows the row, and growing a widget grows its window: on
Wayland that is a buffer re-allocation and a compositor reconfigure, and doing it
on every pointer frame is what made the dock flicker and tear along its edges.
So the room the row can spread into is reserved *once*, before any magnification
starts: =dock_reserve_hover_room()= asks the pure dims for
=dims.hover_headroom_px= (how much the fish-eye can grow within its influence
radius) and sizes the overlay to the row at rest plus twice that. Hovering then
never changes the window's size; the request is re-measured when the pointer
enters and after it leaves, never mid-spread (=state->fisheye_active=).

That leaves a transparent band around the dock, which must not eat clicks: the
surface's input region is cut down to the capsule plus the row
(=dock_apply_input_region()=, from a one-shot frame callback, because a size
request only becomes an allocation on the next frame). It also removes the dead
zone the dock always had above its capsule.

** Auto-hide is a state machine driven by events you cannot see
Tucking the dock away moves the surface off screen with a layer-shell margin, and
what is left on screen is a strip four pixels tall, at the top of the shelf's
magnification headroom (=AUTOHIDE_TRIGGER_STRIP_PX=): it shows nothing, and it is
the only thing the pointer can reach. Three things about that are easy to get
wrong, and all three were:

1. *The input region has to be committed.* While the dock is away the whole
   surface takes input (=lambdock_dock_needs_full_input()=), because the strip is
   the part a dock-shaped region cuts away. But =wl_surface.set_input_region= is
   double-buffered: it takes effect with the surface's next commit, and a dock
   that has finished sliding draws nothing and commits nothing. The compositor
   then keeps the old, dock-shaped region -- which, intersected with the four
   pixels still on screen, is empty. =apply_input_region()= therefore queues one
   draw after setting the region. Without it the strip is dead, and it works
   intermittently, whenever something else happens to produce a frame.
2. *A pointer that never moved still has to be able to reveal.* A pointer resting
   on the strip while the surface slides away underneath it never leaves the
   surface, so the compositor sends it motion, never a crossing. Waiting for an
   enter (or a leave) strands the dock off screen for as long as the pointer stays
   at the screen edge. Motion inside the surface while the dock is away means the
   same thing an enter does (=on_motion_notify()=).
3. *A reveal can arrive in the same frame as the hide it cancels.* The hide is
   requested, `current_margin` is still 0 because no frame has run, and a reveal
   asking for margin 0 therefore looks like "already there"
   (=start_margin_animation()=). Dropping it let the hide finish: the dock parked
   off screen with =is_hidden= FALSE, and nothing would bring it back while the
   pointer stayed on the strip. A slide in flight toward a different target is
   turned around, not ignored.

A leave, on the other hand, is only ignored while the dock is moving -- or has
just stopped (=dock_is_settling()=). Those are the crossings that follow from the
window moving under a stationary pointer, which is what used to bounce the dock at
the screen edge; a leave after that is the user leaving, and hides the dock.

All of it is traced with =LAMBDOCK_DEBUG=1=: crossings with their window
coordinates, the hide margin that was computed, the input region that was
applied, and every slide, each with a millisecond timestamp on the same clock as
=/proc/uptime=. The failures happen on somebody else's compositor with the user's
own hand, so the log is the only way to see the sequence.

** Idle costs nothing
- No tick callback survives a settled animation: both are one-shot and removed on
  completion or on teardown.
- The dynamic-item and trash poll timers skip their work while the dock is off
  screen (=dock_is_off_screen()=), and =dock_items_refresh_polls()= catches every
  item up on reveal, so the first visible frame shows current values.
- =gtk-enable-animations= is cached and refreshed by its notify handler instead of
  being a =g_object_get= per frame.

** An event touches one item, not the row
A title event is dropped when the text did not change (=app_window_set_title()=
and the tracker's visitor both compare before doing anything), accessible text is
memoised on the widget (=lambdock_accessible_update()=), and window state events
only toggle two CSS classes (=dock_item_refresh_window_state()=).

** Where the pixels go
Reflections are at most =SHELF_REFLECTION_BANDS= (16) clipped draws inside one blur
node, down from 40, and they are off by default (=SHELF_DEFAULT_REFLECTION=). Meters
rebuild their paths per repaint, which is fine at one repaint per poll interval and
is listed in [[#rough-edges][Known rough edges]].

When you add work to a per-frame path, ask whether it runs per *item* or per
*frame*, and whether it allocates. The two places to look are
=update_dock_items_fisheye()= and the paint functions in =ui/shelf.c=.

* Portability across compositors
:PROPERTIES:
:CUSTOM_ID: portability
:END:

Two Wayland protocols are optional here, and both are treated as optional. The
backends exercised during development are niri (layer shell and foreign toplevel,
both present) and X11 through XWayland (=GDK_BACKEND=x11=), which has neither.

| Question                                   | API                                | When the answer is no                                              |
|--------------------------------------------+------------------------------------+--------------------------------------------------------------------|
| Wayland with layer shell?                  | ~lambdock_layer_shell_available()~ | the dock is an ordinary window; one log line                       |
| Will a ~gtk_layer_*~ call do anything?      | ~gtk_layer_is_layer_window()~      | callers skip margins, anchors and the exclusive zone               |
| Is there a foreign-toplevel manager?       | =toplevel_tracker.c=               | no running-app items; one warning once the registry is dispatched  |
| Is there a ~wl_seat~?                       | =activate_toplevel_window()=       | activation is skipped with one warning; close/minimize still work  |

Three rules that are easy to get wrong:

- *Never call =gtk_layer_is_supported()= directly.* It asserts that the display is
  a Wayland one, so on X11 it logs a critical /before/ returning FALSE. Use
  =lambdock_layer_shell_available()=, which checks the backend first.
- *Auto-hide is a layer-shell feature.* =hide_dock()= returns early when the window
  is not a layer surface: pretending to hide would leave the dock visible with its
  fisheye frozen. =test_accessibility.c= covers both branches.
- *The foreign-toplevel manager is bound at version 1.* Every event the code uses
  is v1, and the listener table still fills in the v3-only ~parent~ handler,
  because libwayland aborts the process when a compositor sends an opcode whose
  listener is NULL. Raise the version only together with that handler.

Monitor geometry follows the same "ask the most specific source" rule: the dock's
own monitor when it has one, otherwise the monitor the surface landed on (a
monitor-less layer surface is placed by the compositor, which need not be the first
output), otherwise the first monitor.

Minimize, activate and close are *requests*: the protocol says the compositor may
ignore them, and niri has no minimize concept at all. The click policy therefore
degrades to "focus it again" instead of pretending something happened; see
[[#data-flow-click][What a click does]].

* Threading model
:PROPERTIES:
:CUSTOM_ID: threading-model
:END:

| Thread            | Runs                                                        | May touch GTK? |
|-------------------+-------------------------------------------------------------+----------------|
| GTK main thread   | Everything in ~src/~, all widgets, all Wayland listeners    | Yes            |
| Guile REPL thread | Socket server + user-evaluated expressions                  | *No*           |
| Guile GC          | Finalizers / collection (same process)                      | It is not a GTK thread |

Rules:

- UI mutations from Scheme go through ~g_idle_add~.
- Any Scheme object stored across calls must be ~scm_gc_protect_object~'d
  (as ~poll_fn~ is in ~create_dynamic_dock_item~) and unprotected in
  ~free_dock_item~.
- Do not block the main thread. Polling callbacks run there (see pitfall on
  ~cpu-item~ in [[#core-invariants][Core invariants]]).

** Add a new configuration option
:PROPERTIES:
:CUSTOM_ID: add-a-configuration-option
:END:

Touch these in order:

1. =scheme/lambdock/state.scm= -- add the field to ~<dock-config>~
   (constructor + accessor + setter), add it to ~%default-fallback-config%~,
   add a ~configure-dock!~ keyword and its assignment, add a ~get-dock-*~ getter
   (variadic, defaulting to ~'default~), and a ~set-dock-*!~ setter that calls
   ~apply-to-targets~.
2. =scheme/lambdock/core.scm= -- re-export the new getter/setter, and map it in
   ~load-dock-config!~ (accept both ~dock-foo~ and ~foo~).
3. =src/guile_bridge.h= / ~.c~ -- add a typed ~get_*_config_for(path)~ wrapper.
4. Consume it where relevant (usually ~create_dock_instance~ /
   ~reload_dock_instance~).
5. Consider whether it belongs in the C struct in =src/lambdock.h=.
6. Add a test (see below) and update =README.org= and this file's DSL section.

** Add a preset launcher or icon
:PROPERTIES:
:CUSTOM_ID: add-a-preset
:END:

Append to the alists in =scheme/lambdock/presets.scm= (~preset-icons~,
~preset-launchers~). No C changes needed.

** Add a built-in theme
:PROPERTIES:
:CUSTOM_ID: add-a-theme
:END:

Drop a CSS file in =resources/css/=, register it in
=resources/lambdock.gresource.xml=, and add the name to the ~dock-theme~ doc.
Scoping is automatic.

** Add a dynamic poller preset
:PROPERTIES:
:CUSTOM_ID: add-a-dynamic-poller
:END:

Define a ~get-*~ procedure in =items.scm=, add a ~*-item~ builder, export both
from =items.scm= and re-export from =core.scm=. Keep pollers fast and
non-blocking: they run on the GTK main thread.
=items.scm= contains a worked example of why -- the CPU poller keeps its previous
sample instead of sleeping.

** Add tests
:PROPERTIES:
:CUSTOM_ID: add-tests
:END:

C suites are one binary per unit driven by ~tests/test_<unit>.c~. Shared sources
are listed in =meson.build= (~unit_tests~); add your file there. Use
~gtk_init_check()~ to skip display-dependent cases. Extend =tests/test_stubs.c=
if the unit needs ~get_active_dock_states~ / ~unregister_dock_state~.

Scheme suites belong in ~tests/scheme/lambdock_tests.scm~ and are registered
through ~tests/run_scheme_tests.sh~. Assertions run against the real modules
(no C), so they are the cheapest place to lock down ~state.scm=, =items.scm=,
=presets.scm=, =looks.scm=, =loader.scm= and =core.scm= behaviour. The look
recipes are checked there for completeness and range (a recipe that forgets a
shelf number would be inherited from the previous look when applied live), and so
is the loader's "the file wins over the recipe" order.

Whichever suite you touch, ~maak test~ builds and runs all of it on a virtual
display; to iterate on a single case, run that binary directly under ~xvfb-run~
([[#tests][Tests]] explains why a display is not optional).

* Pitfalls & things to be careful about
:PROPERTIES:
:CUSTOM_ID: pitfalls
:END:

These are the traps. Some are latent bugs present in the current tree; fixing
them is welcome, but until then understand them before you build on the affected
code.

** Memory ownership & freeing
:PROPERTIES:
:CUSTOM_ID: memory-ownership
:END:

- *One owner per resource.* ~LambdockState~ owns its ~dock_items~,
  ~window_trackers~, ~monitor~ ref, ~size_group~, and CSS providers. GTK owns the
  widgets once parented/appended. Scheme owns the ~SCM~ records.
- *Free through the right door.* Items → ~free_dock_item~; docks →
  ~destroy_dock_instance~. Never ~g_free~ a struct that has live timers/signals.
- *Detach lists before freeing members.* ~destroy_dock_instance~ and
  ~clear_favorite_dock_items~ both detach the list pointer before iterating so
  re-entrant code cannot walk a half-freed list. Preserve this pattern.
- *~window_trackers~ holds raw Wayland handles, not owned objects.*
  ~free_window_tracker~ and ~clear_window_tracker_dock_references~ are currently
  no-op stubs; do not assume they release anything.
- *GTK widgets are refcounted.* When you take a reference for your own use,
  release it: see
  [[https://docs.gtk.org/gobject/method.Object.ref.html][g_object_ref]] and the
  monitor ref-balancing in ~update_dock_dimensions~.

** Core invariants (these were bugs; do not regress them)
:PROPERTIES:
:CUSTOM_ID: core-invariants
:END:

The issues below were present in earlier revisions and have since been fixed.
They are kept here as guard-rails because each is easy to reintroduce.

- *Idempotent window tracking.* ~dock_item_add_window~ returns the existing
  ~AppWindow~ when a handle is already tracked. ~sync_window_trackers~ runs on
  every reload and ~app_id~ events can repeat, so an unconditional append
  duplicates entries and leaks ~AppWindow~ structs. Keep the guard.
- *Balanced popover counter.* Every increment of ~state->active_popovers~ is
  matched by a decrement. When a dock/item popover is torn down while open its
  ~"closed"~ handler is disconnected, so ~free_dock_item~ and
  ~destroy_dock_instance~ release the slot explicitly. Without this the dock
  never auto-hides again.
- *~app_id~ changes detach cleanly.* ~toplevel_handle_app_id~ removes the handle
  from the item tracking it under the previous id before switching, so no stale
  ~AppWindow~/running indicator is stranded.
- *Pollers must not block.* Dynamic poll functions run on the GTK main thread.
  ~get-cpu-percent~ computes usage between consecutive samples (no ~usleep~); any
  new poller must return immediately.
- *Monitor changes are deferred.* ~on_monitors_changed_cb~ schedules
  reconciliation with ~g_idle_add~ instead of calling ~sync_docks_with_disk~
  synchronously inside ~GListModel::items-changed~.
- *Wayland manager teardown.* ~manager_handle_finished~ and
  ~registry_handle_global_remove~ free the ~MasterToplevel~ bookkeeping, destroy
  the manager proxy, and call ~clear_tracked_windows~ on each dock so no dock
  retains a handle from a departed compositor.
- *Monitor connectors resolve.* ~find_monitor_by_connector~ maps a connector
  name (e.g. ~"DP-1"~) to a
  [[https://docs.gtk.org/gdk4/class.Monitor.html][GdkMonitor]] so ~dock-monitor~
  can target one output; an unknown connector warns and falls back instead of
  failing silently.
- *About dialog is a singleton.* ~on_about_action~ reuses one dialog and destroys
  it on close, and ~activate~ drops the initial ~GSimpleAction~ reference after
  adding it to the action map.
- *Exec matching is bounded.* ~find_dock_item_by_app_id~ only matches ~exec~
  tokens on word boundaries with a minimum length, avoiding substring false
  positives and per-item allocations.
- *CSS scoping reads selectors safely.* ~theme_scope_css_selectors~ tests the
  ~window~ prefix before touching ~sel[6]~. Reading a selector's 7th byte
  unconditionally overflowed the buffer for short selectors such as ~.foo~.
  Keep the prefix check first.

** C ↔ Guile interop hazards
:PROPERTIES:
:CUSTOM_ID: interop-hazards
:END:

- *Resolve procedures, don't guess them.* C reaches Scheme only via
  ~scm_c_public_ref("lambdock core", "name")~. If you rename or stop exporting a
  procedure, C silently degrades to defaults (~g_strdup(default_val)~) instead of
  crashing -- which makes bugs easy to miss. Keep the export lists in =core.scm=
  and =state.scm= in sync with what C asks for.
- *Guard ~scm_is_true~ on lookups.* ~scm_c_public_ref~ returns a value that must
  be checked before calling; the existing helpers do this. Follow suit.
- *String allocation.* ~scm_to_utf8_string~ allocates with Guile's allocator
  and, per its contract, must be released with ~free()~. ~get_guile_string_for~
  can return either a ~scm_to_utf8_string~ result or a ~g_strdup~ fallback, so
  strings it produces (e.g. ~state->theme~, the monitor target) are freed with
  ~free()~, which is valid for both under the default GLib allocator. Follow the
  same rule for any new bridge getter.
- *Protect every stored SCM.* Anything kept in a C struct across calls
  (~DockItem::poll_fn~) must be ~scm_gc_protect_object~'d and later
  ~scm_gc_unprotect_object~'d. Forgetting protection means the GC can collect a
  live thunk. Background: [[https://www.gnu.org/software/guile/manual/html_node/Garbage-Collection.html][Guile garbage collection]].
- *Don't call GTK off the main thread.* The REPL is a different thread. Use
  ~g_idle_add~ (that is exactly what ~scm_reload_dock~ does).

** GTK / GLib hazards
:PROPERTIES:
:CUSTOM_ID: gtk-glib-hazards
:END:

- *GTK main-thread affinity* (repeated because it is the #1 crash source).
- *Signal data is a raw pointer.* ~g_signal_connect(..., state)~ hands GTK a
  pointer that must outlive the connection. Always
  ~g_signal_handlers_disconnect_by_data~ in teardown, and cancel timers/tick
  callbacks first.
- *Re-entrancy.* Destroying a window emits ~"destroy"~; ~destroy_dock_instance~
  guards with ~is_destroying~. If you add a new destroy path, honor the guard.
- *~GtkSeparator~ is not a ~GtkButton~.* Helpers like ~get_item_image_widget~
  rely on ~GTK_IS_BUTTON~ checks to skip separators. Keep those checks.
- *Monitor objects are refcounted.* ~create_dock_instance~ refs, ~destroy~
  unrefs, and ~update_dock_dimensions~ balances its temporary ref. If you cache a
  ~GdkMonitor~ anywhere, ref it.
- *Popovers must be unparented before their parent dies* (see teardown order):
  a [[https://docs.gtk.org/gtk4/class.Popover.html][GtkPopover]] is a child of
  the widget it is anchored to, not a toplevel of its own.

** Build & packaging hazards
:PROPERTIES:
:CUSTOM_ID: build-packaging-hazards
:END:

- *~-Werror~ everywhere.* ~meson.build~ builds with ~warning_level=3~,
  ~werror=true~, plus extra pedantic flags (~-Wshadow~, ~-Wstrict-prototypes~,
  ~-Wvla~, ~-Wformat=2~, ...). Clean compile is mandatory; suppress only in
  vendored/system code.
- *~gnu_symbol_visibility: 'hidden'~.* Non-exported C symbols are hidden. If you
  need two translation units to share a function, declare it in a header (and
  expect ~-Wmissing-prototypes~ to enforce it).
- *Compile-time defines matter at runtime:* ~LAMBDOCK_SCHEME_DIR~ (installed
  scheme dir), ~DEFAULT_GSK_RENDERER~, ~PACKAGE_VERSION~, ~LOCALEDIR~.
- *~%load-path~ pitfall.* ~setup_guile_load_path~ prepends the *relative* path
  ~"scheme"~, so running the binary from outside the repo root (uninstalled) will
  fail to find the modules unless ~LAMBDOCK_SCHEME_DIR~ (the installed path)
  applies. Run from the repo root during development, or install.
- *The generated Wayland protocol sources are build artifacts.* Do not edit them;
  edit ~protocols/*.xml~ or rely on the ~wlr-protocols~ package.
- *The Guix manifest needs the =bin= output of glib.* ~gtk~ propagates glib's
  default output only, and ~glib-compile-resources~ lives in =glib:bin=. Without
  it ~meson~ aborts while measuring =gnome.compile_resources()=:
  ~Dependency 'gio-2.0' tool variable 'glib_compile_resources' contains
  erroneous value: 'glib-compile-resources'~. A development shell often hides
  this because the host's copy is on ~PATH~; a CI container does not.
  =manifest.scm= therefore lists ~(list glib "bin")~.
- *Translations are generated too.* ~po/*.po~ are edited, ~lambdock.pot~ is
  produced by ~maak i18n-update~; do not edit the template by hand.
- *Meson options are documented upstream* if you need to add a feature toggle:
  [[https://mesonbuild.com/Builtin-options.html][built-in options]].

** Configuration semantics
:PROPERTIES:
:CUSTOM_ID: configuration-semantics
:END:

- *Config keys are aliased.* Both ~dock-foo~ and ~foo~ are accepted by the
  loader. Keep new options consistent.
- *~'default~ shadowing.* The primary ~settings.scm~ is stored under both its
  path and ~'default~. Multiple ~settings-*.scm~ files each get their own
  record; be deliberate about which key you read.
- *~is_app_excluded~ is case-insensitive* (~g_ascii_strcasecmp~) and is applied to
  name, icon, and exec on the C side and to ~app_id~ on the tracker side --
  exclusions can therefore suppress more than you expect.
- *Item matching is heuristic.* ~find_dock_item_by_app_id~ matches ~app_id~,
  ~icon~, ~name~, and does substring matching on ~exec~; this can associate a
  window with the wrong item. Understand it before extending the matcher.
- *Item lists are rebuilt on reload, window state is not.* A reload clears only
  the favorite items ([[#dock-item-lifecycle][Dock item lifecycle]]); anything you
  cache on a ~DockItem~ that is /not/ a favorite will outlive the config change.

* Glossary
:PROPERTIES:
:CUSTOM_ID: glossary
:END:

| Term                  | Meaning                                                                 |
|-----------------------+-------------------------------------------------------------------------+
| ~LambdockState~        | Per-dock C state; one GTK window                                           |
| ~DockItem~             | A dock entry: favorite launcher, dynamic widget, separator, or tracked app |
| ~AppWindow~            | A (Wayland handle, title) pair tracked by a ~DockItem~                     |
| ~MasterToplevel~       | C struct pairing a raw toplevel handle with its title/app_id              |
| ~window_trackers~      | Per-dock ~GList~ of raw toplevel handles used for show-when-clear logic    |
| ~<dock-config>~        | Scheme record holding one dock's configuration                             |
| ~*dock-configs*~       | Scheme hash table of ~<dock-config>~ keyed by path and ~'default~          |
| Scoped CSS            | Theme selectors rewritten to ~.theme-<name> ...~ so docks do not leak styles |
| Fallback dock         | The dock spawned when no ~settings*.scm~ exists (~config_path == NULL~)     |

Words that belong to the wider stack (compositor, layer shell, GSK, thunk,
foreign toplevel, XDG, ...) are defined in
[[file:README.org::#glossary][README: Glossary: the words in this document]].
