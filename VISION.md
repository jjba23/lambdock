# Vision

lambdock is a dock whose configuration is a Scheme program, in one process, with a REPL socket into the running dock. The C half is GTK4, `gtk4-layer-shell` and the Wayland protocol listeners; the Scheme half decides what exists, where the shelf sits and what a meter reads. This document is about the parts of that arrangement the project has not yet made good on: the place where a Lisp that is the configuration language has not become a configuration that can be checked, extended, or explained by the dock itself.

## Where lambdock is today

The split is real and defended. `src/` is C17 with `-Werror`, LTO, PIE and a warning set that includes `-Wshadow`, `-Wmissing-prototypes`, `-Wformat=2` and `-Wvla`, and there is no deprecated GTK3 pattern left anywhere in it — `gtk_container_*`, `gtk_box_pack_start`, `gtk_widget_show` and `gtk_window_new` all return nothing when grepped. Nine Scheme modules under `scheme/lambdock/` hold the policy: `core`, `state`, `items`, `loader`, `presets`, `looks`, `logger`, `layout` and `prefs`. Settings are evaluated into the embedded image at start and again on every save; a setter goes through `apply-to-targets` and ends in `trigger-ui-reload!`, which is a `(reload-dock!)` on the C side.

That last path is the whole architecture in one sentence, and it is worth knowing before proposing anything: state lives in Scheme records, the C side keeps a mirror it can draw from, and the only sanctioned way to change anything is a setter that marks the mirror for reload on the frame clock. There is one documented exception to the tidiness — Guile itself is not safe from two threads, so the REPL thread never calls into GTK and every Scheme value held across a call is protected from the collector. Any extension that ignores that will work until the first garbage collection.

The feature set is unusually complete for a dock: launching and focusing, a window popover that closes or minimises individual instances, folder stacks as a grid or a list, a searchable launchpad built from XDG desktop entries, the freedesktop trash with artwork and an item count, drag and drop that reorders items and accepts a `.desktop` file or a folder, fish-eye magnification, dock scrolling, dynamic widgets with Scheme pollers, nineteen themes and the looks that set a whole dock in one line, in either a floating capsule or a full-width taskbar.

The accessibility work is worth separating from that list, because it is the part of a dock that is almost always missing. The dock, its menus, its stacks and the launchpad are reachable from the keyboard with arrows, Home/End, the Menu key and Ctrl+Arrow to rearrange; every icon announces its name and state; focus rings are visible; and reduced motion is honoured from the dock's own setting or the desktop's accessibility preferences. `test_accessibility.c` covers both branches of the auto-hide layer logic, which is the sort of test that only exists in a project that has decided accessibility is a behaviour rather than a colour.

Two backends sit behind one window model since v1.3.0. On Wayland the dock is anchored through layer shell and reads `zwlr_foreign_toplevel_manager_v1`; on X11 it claims its edge through EWMH, reads `_NET_CLIENT_LIST` and the per-window properties, publishes a `_NET_WM_STRUT_PARTIAL` so maximised windows stop at it, and gives up only the slide. `LambdockToplevel` is the handle every module passes around — a proxy on Wayland, a window id on X11 — so the docks, the popover, the click policy and the item wording are written once. A session with neither protocol reports which half it is missing.

What the project says about itself is the best account of its own constraints. `HACKING.org` documents four layers and the dependency rules between them, the rule that a decision is extracted into `src/core/` even when its only caller is a protocol listener, the rule that a kind is a table row rather than a switch, and the thread model that matters most: the Guile REPL runs on its own thread and may not touch GTK, so every UI mutation from Scheme goes through `g_idle_add` and every Scheme object held across calls is `scm_gc_protect_object`'d. It also keeps an honest list of what is still rough — `dock_item.c` at about 1,900 lines, `preferences.c` at about 1,300, `main.c` holding startup, disk sync, overlay CSS and the REPL primitives together — and says what the first move is in each case.

The test surface is the reason the C half can be refactored: thirty-odd test programs, `tests/scheme/lambdock_tests.scm` beside them, sanitizer builds, `/perf/` tests against the render counters, and regression tests named after the bug they prevent — the launchpad's buffer growth measured in RSS, the accessibility suite pinned to a named icon theme so it stops depending on the maintainer's desktop. Translations live in `po/` for Catalan, German, Spanish, French, Italian and Dutch, and packaging exists for Arch, Debian, openSUSE and Flatpak.

The performance discipline is documented as a set of decisions rather than a claim: paint continuously and lay out coarsely, one layout pass per frame rather than per event, the surface keeps its size while hovering so a fish-eye sweep does not renegotiate it, auto-hide driven by events that are not visible from inside the dock, and idle costing nothing. `render_stats` and the `/perf/` tests are how those decisions are checked, which is the right order — a speedup claimed without a number is not a speedup.

Even the showcase is engineered. `tools/record-demo/` records from a scripted nested niri session, with `wlr-virtual-pointer` XML and a small `vptr.c` to move a synthetic pointer, a Python controller staging scenes, `measure_dock.py` to check the geometry it is filming, a generated overlay and a shell encoder — because a GIF of a dock is not credible unless it is a recording of the dock.

## The vision

1. **A settings file that cannot be silently wrong.** `settings.scm` is evaluated, and a misspelt binding, a string where a number belongs or an unknown theme symbol leaves the default in force with nothing to say. In a few years `configure-dock!` and the loader validate the resolved configuration — every option named, every value in its domain, every item kind known — and report the offending binding with enough of the file to find it. A program for a configuration is the right design; a program with no preconditions is only half of one.
2. **Item kinds are extensible from Scheme.** `HACKING.org` states the rule that a kind is a table row and not a `switch`, and today the table is in C: `create_*_dock_item` constructors build the widget for each kind. A hyper-hackable dock should let a module register a kind — an icon, a label, a poller, an activation — and have C build it from a recipe. This is the difference between "the configuration is a program" and "the configuration is a program that may only choose from the menu".
3. **What the dock cannot do, the dock says.** Layer shell, the foreign-toplevel manager and a `wl_seat` are all probed already (`lambdock_layer_shell_available`, `toplevel_tracker`, `activate_toplevel_window`), and the answer goes to a log line. Mutter implements neither layer shell nor the toplevel protocol, so on GNOME the dock is an ordinary window and auto-hide is not available; niri has no minimise, so a click degrades to focusing. Those are honest degradations reported to the person who needs to know — in the About row, in the Preferences window, in the tooltip on the item — rather than to whoever is reading stdout.
4. **The REPL is the documented way to develop a dock, not an easter egg.** `dock-enable-repl?` plus a Unix socket already gives a live image that can read state, replace it and watch the next frame draw. Making it a supported interface means a versioned set of primitives, a published protocol so a client can be written in another language, and the guarantee that everything the Preferences window can do, a form can do.
5. **Themes and looks are distributable units.** A theme is a CSS file, a look is a recipe of settings, and both are currently data inside the tree. A dock whose settings are a program should be able to load a look from `~/.local/share/lambdock/looks/`, so improving the dock's appearance is a file somebody can send rather than a patch to the project.

The five share a subject: the interface between the user's program and the dock's own machinery. Statement 1 is about what the interface accepts, 2 is about what it can add, 5 is about what it can carry between machines, 4 is about how it is explored, and 3 is about what it can consult when the answer is "not on this compositor". That is the right place to spend the next few years, because everything else in the dock — the rendering, the animation, the window tracking, the two backends — is already unusually settled, and the parts that are not are named in the project's own developer guide.

## Features that are in scope and not built yet

Each of these is a seam the code has already cut.

- **Configuration validation.** The loader already extracts a fixed set of conventional bindings and applies overrides from `preferences-settings.scm`. *The hard part* is that the file is arbitrary Scheme — a settings file may compute its item list with `map` over a directory — so the check has to validate the resolved value, and it has to be able to say "this came from a procedure, I cannot see inside" without treating every computed value as suspicious.
- **A Scheme-side kind registry.** The rule that a kind is a table row exists on the C side. *The hard part* is GTK: building a dock item means widgets, CSS classes and signal connections, so an extension point is not a data structure but a recipe C interprets, and getting that wrong produces a plug-in API nobody can use without reading C.
- **Capability reporting in the UI.** Every probe exists and every answer is logged. *The hard part* is that a capability is not a boolean — auto-hide needs layer shell, activation needs a seat, minimise needs a compositor that has the concept — so the report has to be about features a user would want, not protocols.
- **Auto-hide on X11.** The README's most honest sentence: what is given up there is the slide, because auto-hide needs a surface a compositor can push off screen. *The hard part* is that the X11 alternatives all trade something worse — an unmap loses the fisheye and the animation, an override-redirect window fights the window manager.
- **A published REPL protocol.** The primitives exist and are documented in `docs/repl.org` with Geiser and `socat` recipes. *The hard part* is that a stable protocol constrains the getters and setters that are currently free to change, and the project's own answer to "how do I do this" is a live image whose whole appeal is that it is not a protocol.
- **A REPL client that is not Emacs.** Geiser and a raw socket are the two documented routes, and both assume a Lisp person. *The hard part* is that the interesting client is probably a small GUI slider panel, and building one means a protocol first — which is the previous item.
- **Splitting the three big files.** `dock_item.c`, `preferences.c` and `main.c` are named in `HACKING.org` with a first move each. *The hard part* is that they are not messy, they are large and dense, and the split has to keep thirty test programs and the render budget green while it happens.
- **A user theme directory.** `dock-theme 'none` exists for hand-written CSS, and the nineteen built-in themes are shipped data. *The hard part* is that a theme and a look are not the same kind of thing — one is a stylesheet with state classes, the other a list of settings — and a distribution format has to keep them distinguishable.
- **The icon chain, exposed.** `lambdock_icon_search_paths_build()` takes the directories as inputs and is tested, and `setup_icon_theme()` applies the list; a missing name logs a warning that GLib's fatal-warning policy turns into an abort in tests. *The hard part* is that the resolution is a chain — item DSL, preset, desktop entry, icon theme, fallback — and the interesting report is not which name failed but which of the five steps chose it.
- **The taskbar's window titles.** `dock-mode 'taskbar` and `dock-show-window-titles?` exist alongside a full-width Luna geometry. *The hard part* is that a title is the one piece of dock text that is arbitrary and changes without notice, so the truncation, the direction and the font size are a layout policy the item text module has to own rather than a label property.
- **Preferences parity.** `prefs.scm` reads and writes `~/.local/state/lambdock/preferences-settings.scm`, which overrides the configuration file. *The hard part* is that two sources of truth for one value is exactly the arrangement the project avoids elsewhere, so the precedence has to be documented where a user will find it — and every new option is a decision about whether it belongs in the Preferences window at all.
- **The `+` and the launchpad's scan.** The launchpad is built from XDG desktop entries and the scan is repeated per open since the window is destroyed on hide to keep RSS flat. *The hard part* is that this is the correct trade for a dock that is opened occasionally and the wrong one for a dock that is opened constantly, so the cache belongs somewhere with an invalidation story — a file watcher on the desktop-entry directories, most likely.

## New features that would be worth having

- **`lambdock --check`.** Load the settings file, validate it, report every unrecognised binding and out-of-domain value, and exit non-zero — starting nothing. *Why it is worth having:* the settings file is the one part of the dock that a user edits by hand, and the failure mode of a typo is a dock that looks almost right.
- **An item-kind playground.** A second, deliberately ugly dock instance that a Scheme module drives with test items, so a new kind can be developed and seen without editing the real configuration. *Why it is worth having:* the dock's own architecture makes this cheap — a second `lambdock-state` is a value — and it is the tool the kind registry will need to be usable.
- **A render overlay.** `render_stats` and the `/perf/` tests already measure frame cost. A toggle from the REPL that draws the current frame time, the number of items and the poller cost on the dock itself would make the performance work visible where the work happens. *(Speculative in form; the numbers already exist, which is usually the right precondition.)*
- **A settings migration.** Every option added is an option some settings file does not have, and every rename is a settings file that stops working silently. A `~/.config/lambdock/settings.scm` written against v1.3.0 should not have to be rewritten to be understood. *Why it is worth having:* the project has already renamed things, and the compatibility story is currently "read the changelog".
- **A dock that can be captured as text.** Serialise the resolved configuration back out as a `settings.scm` that would produce the current dock, including whatever the Preferences window changed. *Why it is worth having:* it is the inverse of the loader, it makes a bug report reproducible, and it is the only honest way to answer "what is my dock actually doing" without a REPL.
- **A poller budget.** Every dynamic item is a Scheme thunk on the main thread. A budget — total poll cost per frame, reported when a configuration exceeds it — would turn the `cpu-item` hazard from a note in the developer guide into a rule. *(Speculative in mechanism, and it is the kind of thing that is easier to measure than to enforce.)*
- **A scenario format for the demo recorder.** `tools/record-demo/` already drives a nested session with a virtual pointer, and `controller.py` stages scenes. A declarative scenario — a list of steps the recorder plays — would make the showcase reproducible from a file rather than a Python script. *(Speculative; it is already reproducible, so the win is readability.)*
- **A dock that mirrors another dock.** Multi-dock support exists per monitor and per connector. A mirror is a second dock on the same monitor with a filtered item list — the same value read twice — which is the shortest route to the "one shelf of apps, one shelf of downloads" layout people fake today. *(Speculative in demand, cheap in code.)*
- **A "why is this item here?" inspector.** For any item, show the launcher that created it, the desktop entry it resolved, the icon name it found, and the poller that drives it. *Why it is worth having:* the dock resolves a chain — item DSL, preset, desktop entry, icon theme, window — and the chain is the explanation for almost every "why is my icon wrong" report.
- **A dock that survives a compositor restart.** Window tracking is a listener; when a compositor restarts, the foreign-toplevel proxies are gone and the dock rebuilds them. A visible "reconnecting" state, and a guarantee that the item list and the item order are untouched, would make a niri restart a non-event. *Why it is worth having:* the state is already a value the C side mirrors, so the recovery is mostly a matter of not doing anything clever.
- **A shelf for the trash and the stacks.** The trash and the stacks are the two features that produce content rather than launch things, and both deserve a place the launchpad can reach. *Speculative in form, and it is really a question about whether the dock should have a second mode rather than another item kind.*

The pattern is the same one the project already uses for its own development: make the machinery observable. A dock with a REPL, a render counter, a capability probe and an icon-chain inspector is a dock whose bugs arrive with an explanation attached, which is worth more than any single feature in this list.

## Contributions that would move the needle

1. **One option, validated end to end.** Pick an option with a clear domain — `dock-icon-size`, `dock-position`, `dock-mode` — and make an out-of-domain value raise with the binding's name, in the loader and in `configure-dock!`. *Why it is a good task:* it is a day's work that produces the pattern for every other option, and it needs no C at all.
2. **Capability reporting, one row.** Add a row to About that names what the current session cannot do and why, using the probes that already exist. *Why it is a good task:* it is the cheapest possible answer to the most common support question, and it teaches the portability matrix that `HACKING.org` documents.
3. **A test that prevents a documented regression.** `HACKING.org` keeps a list of invariants that were once bugs. Each one of them deserves the test named after it. *Why it is a good task:* the list is already written, the failures are already understood, and the tests are the reason the C half can be restructured at all.
4. **The `main.c` split it asks for.** Move the REPL primitives into a `repl.c`. *Why it is a good task:* it is named in the project's own TODO, it is mechanical, and it makes the interface that statement 4 is about a file somebody can read in one sitting.
5. **A look in a file.** Make `look-settings` load a look from `~/.local/share/lambdock/looks/`, and ship the built-in ones through the same path. *Why it is a good task:* it turns a table in Scheme into a distribution format without changing a single existing behaviour.
6. **A theme that is not a recolour.** Nineteen themes is a lot of taste and not much range: most are dark shelves with different accents. *Why it is a good task:* it would find out whether the state classes and the shelf geometry are actually sufficient, which is the question every bit of theming documentation quietly assumes.

The ranking is value per hour, and the first two are small: a validated option and a capability row are each a day, and together they remove the two questions a new user asks first. Item 3 costs nothing but attention — the list of invariants is already written down — and it is the one that protects every later refactor. Item 6 is the most fun and the least urgent, which is why it is last and why it is the one most likely to teach something.

What is deliberately not on the list: another configuration option, another preset launcher, another icon in the default dock. The surface is large enough that adding to it now would make statement 1 harder rather than easier, and the project's own `HACKING.org` is refreshingly unsentimental about the difference between a feature and a liability.

## Compared to related projects

| Project | What it is | Where lambdock differs |
|---|---|---|
| Plank | The elementary OS dock, C with a GObject config API | The closest ancestor in spirit and the closest in implementation language. Plank is X11-first and configured through a settings window and a key file; lambdock is Wayland-native, and its configuration is a Lisp program with a REPL into the running process. |
| Latte Dock | The KDE dock, in Qt, with unlimited configurability and per-applet settings | The most configurable dock ever built, and now unmaintained — which is the cautionary comparison this project should keep in view. Latte's configuration surface was its cost; lambdock's answer is to make the surface a language rather than a settings tree, but the maintenance risk is the same one. |
| Dash to Dock | A GNOME Shell extension in JavaScript that turns the overview into a dock | It lives inside the shell and inherits everything; lambdock is a separate process that needs protocols and reports when it has none. Also the one project lambdock cannot replace, because GNOME provides neither layer shell nor the toplevel protocol. |
| nwg-dock | A GTK dock for sway and Hyprland, configured by command-line flags | The nearest neighbour in the Wayland-native space and the closest in intent. nwg-dock is configured by flags and has no window popover, no stacks, no launchpad and no live image; lambdock's argument is that a dock has enough state to deserve a language. |
| Cairo-Dock | An OpenGL dock with applets and an elaborate plug-in API | The applet API is the thing lambdock lacks and probably should have — in Scheme rather than C. Cairo-Dock's rendering is a different world; its extensibility is the model to study. |
| Waybar | A GTK4 layer-shell bar with modules, CSS and a JSON config | Complementary rather than competing: Waybar is a status bar that can list tasks, lambdock is a dock that tracks windows. Waybar's config is a data file and its styling is real CSS; lambdock's is a program and its styling is CSS with state classes. |
| The KDE and Xfce panels | Desktop-environment panels with task managers | Enormous feature surfaces that come with the desktop. lambdock's feature set is comparable for the dock-shaped part and its deployment is a single binary plus a settings file. |
| macOS Dock and Windows taskbar | The two docks everyone has used, closed source | The reference for behaviour, badly imitated by a decade of Linux docks: magnification done right, minimise-into-dock, and a launch animation that reads as a consequence rather than a decoration. lambdock's fish-eye and its poof are the honest attempts at the first and the third; the second is unavailable on niri because there is no concept of a minimised window. |

What the others do that lambdock could still add: Cairo-Dock's applet model is the mature version of the item-kind registry in statement 2, and it is worth reading before designing one. Waybar's CSS is a genuinely good styling contract — a theme can be written without knowing the program — and lambdock is close to it already. Latte's per-dock configuration is the feature multi-dock users miss, and `~/.local/state/lambdock/preferences-settings.scm` is the beginning of the same idea.

The macOS Dock comparison deserves a caveat, because imitating it is where most Linux docks have gone wrong. What makes it feel correct is not the magnification curve, it is the coupling: a window minimises into its icon and comes back out of it, so the dock is a place windows go rather than a launcher that also lists them. `zwlr_foreign_toplevel_manager_v1` has no such concept, and niri has no minimise at all, so the coupling is not available. A dock on Wayland can imitate the appearance and the animation, and it cannot imitate the behaviour; being clear about that is more valuable than a closer imitation.

Where lambdock is ahead and should stay ahead: the live image. No other dock can be inspected and mutated while it draws, and the record of that being useful is that the project's own showcase was recorded by driving the dock from a REPL. The second advantage is that the same window model serves two protocols, which is why an X11 session gets a dock rather than an apology. The third is that the settings language is a language, so a dock layout can be computed by a program that reads a directory — a feature no settings tree will ever have.

It is worth being honest about the fourth difference, which is not an advantage but a choice: lambdock is GTK4 and C, and that is why it is small enough to understand and why it will never be a platform. Plank, Latte and Cairo-Dock all died of scope; the ones that survive — Dash to Dock inside the shell, nwg-dock with flags — survive by belonging to something else or by refusing to grow. lambdock's position is that the growth belongs in the user's Scheme rather than in the binary, and the five statements above are the test of whether that position holds.

## In the long run

The long bet is that a desktop component should be a small program with a big interface, rather than a big program with a settings window. lambdock's interface is its Scheme image, and everything the project has built — the getters and setters, the reload path, the REPL — is in service of the idea that inspecting a running dock and changing it are the same operation.

That is a claim with a testable consequence: if the interface is good, then a dock somebody else wants should be expressible without a patch to `src/`. Today it mostly is — the item DSL, the presets, the looks and the layouts cover a great deal — and the exception is exactly statement 2, where a genuinely new kind of widget still needs C. Closing that gap is the work that would make the claim true rather than nearly true.

The second bet is about survival. Latte Dock is the proof that configurability does not buy maintenance, and the reason lambdock has a chance is not its feature list but its tests: thirty programs, sanitizers, a render budget and a discipline of extracting every decision into a pure function. Those are the things that let somebody else change the C later, and somebody else changing the C later is the only real measure of whether a project outlives its author's attention.

The third bet is that Wayland's protocol-shaped fragmentation is a feature to be honest about rather than a problem to be smoothed over. Layer shell is not everywhere, the toplevel protocol is not everywhere, and a dock that says so — per compositor, in the interface — is more useful than one that pretends the difference does not exist until the user notices.

What would falsify these bets is worth stating. If Wayland's desktop-portal work ever gives a standard dock an official protocol, the dual backend stops being an advantage and becomes compatibility debt — a good kind of debt, but debt. If GTK5 arrives with a different layer-shell story, the C half is a rewrite of the parts that touch the surface, and the Scheme half is the part that survives, which is the argument for the split. And if Scheme's reach among desktop hackers stays where it is, the item-kind registry in statement 2 will be a feature with almost no users — which does not make it wrong, but does mean it should be built when somebody asks for it rather than in anticipation.

## How to read this document

The in-scope list is the project's own honesty reflected back: several of those items are already named in `HACKING.org`, with a first move each. The rest are proposals, and the speculative ones are marked. `NEWS.org` remains the record, and no item here should be read as scheduled because of the order it appears in.

The most useful way to read the five statements is as one sentence: the dock should treat its own configuration the way it already treats its own window model — as something with one owner, one shape and one place to look when it is wrong. Everything else follows from that, including the decision not to add another option.

*This document describes intent, not commitments; the code, its thirty test programs and the changelog remain the only account of what lambdock does.*
