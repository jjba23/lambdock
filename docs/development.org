* Translation status
:PROPERTIES:
:CUSTOM_ID: translations
:END:

This project aims for accessibility and ease-of-use for users. For this purpose,
we try to translate lambdock to all languages we can maintain. See below the
status of translations for this project:

| Language      | Status |
|---------------+--------|
| English 🇬🇧     | 100%   |
| Catalan 🇪🇸     | 100%   |
| Dutch 🇳🇱       | 100%   |
| French 🇫🇷      | 100%   |
| German 🇩🇪      | 100%   |
| Italian 🇮🇹     | 100%   |
| Portuguese 🇵🇹  | 100%   |
| Spanish 🇪🇸     | 100%   |

Translations live in ~po/~ and are managed with
[[https://www.gnu.org/software/gettext/][GNU gettext]]: ~cargo run -p xtask --
i18n~ refreshes the =.pot= template and merges it into every =.po=, and the
~maak i18n-update~ task is that command inside the pinned environment.  Adding a
new language is a matter of adding its code to ~po/LINGUAS~.
If your language is missing, or if a string reads badly in yours, that is a
welcome patch -- and a good first contribution.

*** Read the guide first
:PROPERTIES:
:CUSTOM_ID: read-the-guide
:END:

New to the codebase? Start with the [[file:../HACKING.org][Developer Onboarding & Architecture Guide]], an extensive walkthrough of the Rust core, the embedded GNU Guile Scheme
engine, the bi-directional data flow, the full dock/item/window lifecycles, the
build and test workflow, and the common pitfalls to watch out for. It covers the
threading model, memory ownership rules, GTK/GLib hazards and the invariants that
used to be bugs.

*** Hacking with ~maak~
:PROPERTIES:
:CUSTOM_ID: hacking-with-maak
:END:

~lambdock~ uses [[https://codeberg.org/jjba23/maak][Maak]], a Scheme task
runner, so the build recipes are readable Lisp rather than opaque Makefiles. Run
~maak <task>~ from the repository root:

| Task               | What it does                                                          |
|--------------------+-----------------------------------------------------------------------|
| ~maak run~         | Build and run lambdock inside the pinned Guix environment.            |
| ~maak build~       | Build the dock, release profile, inside the pinned environment.       |
| ~maak test~        | Rebuild and run the suite in the pinned Guix environment: the tests, then the lints. |
| ~maak debug-run~   | Rebuild and launch under ~gdb --args~.                                 |
| ~maak repl~        | Start a development REPL for the project.                             |
| ~maak vendor~      | Regenerate ~rust/vendor/~ and ~.cargo/config.toml~ after a dependency change. |
| ~maak add-libs~    | Regenerate ~.ccls~ with the right Guix package flags.                  |
| ~maak i18n-update~ | Refresh the gettext =.pot= and =.po= files.                            |
| ~maak deb-build~   | Build the Debian package (unsigned).                                  |
| ~maak rpm-build~   | Build the RPM packages and lint them.                                 |
| ~maak arch-build~  | Build the Arch package and run ~namcap~.                               |
| ~maak nix-build~   | Build the Nix package (~nix-test~ runs the flake checks).              |
| ~maak flatpak-build~ | Build the Flatpak bundle.                                           |
| ~maak container-build~ | Build the Podman/Docker image (~container-run~ runs it).          |

*** The development environment
:PROPERTIES:
:CUSTOM_ID: development-environment
:END:

~manifest.scm~ is the whole toolchain, pinned by ~channels.scm~, and ~flakes.nix~
mirrors it for Nix.  Either way the shell carries what a Rust project needs and
nothing that only the build machine needs:

- ~rustc~ and ~cargo~ from the pinned Rust, and the same version's ~tools~ output:
  ~cargo clippy~, ~rustfmt~ and ~rust-analyzer~.  They are one version on purpose
  -- a clippy from the host is a second toolchain, and its artifacts do not run
  in this shell.
- ~rust-src~, which is the standard library's sources: ~rust-analyzer~ reads them
  for std's signatures and documentation.  Guix's ~rust-analyzer~ wrapper exports
  ~RUST_SRC_PATH~ for it; the Nix shell sets it in ~shellHook~.
- ~gdb~, which is what ~maak debug-run~ launches, and ~adwaita-icon-theme~, which
  is what makes the icon in the item tests resolvable.

Enter it with ~guix shell -m manifest.scm~ (or ~nix develop~, or ~direnv allow~
-- the repository ships an ~.envrc~ that evaluates the same manifest).  Then:

#+begin_src sh
cargo build --offline --locked      # the dock
cargo test --offline --locked       # the suite
cargo clippy --offline --locked --all-targets
cargo fmt
#+end_src

~maak test~ is those last two inside the shell, with the cargo home pinned so
~cargo clippy~ finds the shell's clippy rather than the host's under rustup.

For ~rust/src/~ the language server is ~rust-analyzer~, which needs no
configuration in the shell.  Two target directories exist and neither is the
other: from the repository root ~cargo build~ writes =./target=, while
~maak test~ builds in =rust/target= because it changes into =rust= first.  Run
~./target/debug/lambdock~ -- =./rust/target/debug/lambdock= can be days old.

*** Tests
:PROPERTIES:
:CUSTOM_ID: tests
:END:

One command, from the repository root:

#+begin_src sh
maak test
#+end_src

That is ~cargo clean~, ~cargo test~ and ~cargo clippy --all-targets~ inside the
pinned environment.  The suite needs no display: every test is a decision, so it
runs where the shell does -- on a CI runner with no compositor, over SSH, in a
container.

- *Rust unit tests* (~rust/src~, ~#[cfg(test)]~ beside the code): 310 of them.
  The pure decisions -- the dimension arithmetic, the easing and the slide, the
  item wording, the EWMH rules, the poller budget, the render counters -- plus the
  seams: the theme selector rewriting, the settings export round trip, an item's
  key, the record that owns its text, and the pure reorder on a slice that replaced
  a `GList` delete-and-insert.
- *Scheme unit tests* (~tests/scheme/lambdock_tests.scm~, run by ~cargo test~ as
  the ~scheme~ integration test): 348 assertions over the pure-Guile
  configuration engine -- state, items, presets, the loader, layout overrides and
  core -- with no display and no GTK.
- *The widget layer* -- dock windows, popovers, the launchpad, drag and drop -- has
  no automated coverage today: it was verified by running the dock, and porting it
  as display-gated tests is the open work listed in
  [[file:../HACKING.org][HACKING.org]].

~cd rust && cargo test --offline --locked~ runs the same suite outside the shell.
